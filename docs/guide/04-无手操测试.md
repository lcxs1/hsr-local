# guide/04 · 无手操测试（Bot / 抓包回放 / 真机驱动）

> **状态**：现行　**适用版本**：4.7.51（build 17100438）/ 4.6.54 / 4.7.0　**最后修订**：2026-11-13

目标：**先把“测服务端”和“开客户端”解耦**。绝大多数改动（handler、字段、包序、状态机）
不该靠人手点游戏来验证；真机只留给“客户端会不会渲染/崩溃”这一类问题，而且那部分也尽量
由服务端驱动、脚本取证，人只负责最后看一眼截图。

---

## 1. 三层测试与各自能测什么

| 层 | 入口 | 需要客户端 | 能测 | 测不到 |
|---|---|---|---|---|
| L1 离线回放 | `scripts/replay_flows.py`、`hsr/replay.py` | 否 | handler 逻辑、包序、状态字段、存档副作用 | UDP/KCP/帧/编解码、会话状态、真实时序 |
| L2 无头客户端（本次新增） | `scripts/bot_smoke.py`、`hsr/tools/bot.py` | 否 | 上面全部 + 握手/KCP/帧/proto/心跳/会话/多包交互 | 客户端渲染、客户端 NRE、资源校验、UI |
| L3 真机驱动 | `scripts/game_test.ps1` + `/debug/*` + Lua | 是 | 黑屏/闪退/UI/资源/字段语义 | 需要人维护坐标或客户端 API 探针 |

经验比例：一次改动的 80–90% 应该在 L1+L2 就被拦住；L3 只在“这条链必须看画面”时跑一次。

## 2. L2：无头客户端（`hsr/tools/bot.py`）

它把真实客户端最外面那层照抄了一遍：20 B UDP 握手 → KCP（`u32_le_token`）→
`9D74C714` 帧 → protobuf；然后按场景发 `CsReq`、收 `ScRsp`/`Notify`。
用的是服务端同一套 `hsr.net.*` / `hsr.protocol.*`，所以**帧、KCP、注册表、字段映射都是真的**，
只少了 Unity 渲染。

```powershell
# 默认 profile（4.7.51）：登录 → 场景 → 换队 → 命途 → 凝滞虚影 → 再来一次 → 心跳
.\.venv\Scripts\python.exe scripts\bot_smoke.py

# 4.6.54 全量：再加混沌回忆 上半 → 换组 → 下半 → 结算 → 退出
.\.venv\Scripts\python.exe scripts\bot_smoke.py --profile 4.6.54 --challenge

# 4.6.54 异相仲裁：GetChallengePeakData → Start → 场景 Notify → 战斗 → 结算 → Confirm → Leave
.\\.venv\\Scripts\\python.exe scripts\\bot_smoke.py --profile 4.6.54 --peak

# 连已经在跑的服务端（不再自己起进程）
.\.venv\Scripts\python.exe scripts\bot_smoke.py --no-spawn --port 23301

# 机器可读
.\.venv\Scripts\python.exe scripts\bot_smoke.py --json
```

脚本默认自己起一个**一次性服务端**：随机端口、存档写到 `.tmp/bot-smoke/saves/`，
不碰 `saves/player.json`，跑完就杀进程；`--keep` 保留现场，失败时自动打印服务端日志尾部。

当前基线（2026-11-13 实测）：

| profile | 场景 | 结果 |
|---|---|---|
| 4.7.51 | 核心链 | 14 passed / 1 skipped（`QuitBattleCsReq` 还不在 140 条表里）/ 0 failed |
| 4.6.54 | 核心链 + 混沌回忆（`--challenge`） | 23 passed / 0 skipped / 0 failed |
| 4.6.54 | 核心链 + 异相仲裁（`--peak`） | 22 passed / 0 skipped / 0 failed |
| 4.6.54 | 核心链 + 混沌回忆 + 异相仲裁（`--challenge --peak`） | 30 passed / 0 skipped / 0 failed |

> `--challenge` 跑的是**真 wire**：`StartChallenge` → `SceneCastSkill` → `PVEBattleResult` →
> 服务端推 10 个换半场包 → 下半 `SceneCastSkill` → 结算 Notify → `LeaveChallenge`。
> 这和 `game_test.ps1` 里那条“下半黑屏”链是同一条服务端路径，只是没有客户端渲染。

### 2.1 怎么加一条新场景

在 `scripts/bot_smoke.py` 里照 `run_core` 的写法加步骤即可：`bot.call_empty("XxxCsReq")`、
`bot.call(req, "XxxCsReq")`，断言看 `pkt.msg.retcode` / 具体字段；
服务端主动推的包用 `bot.drain(0.5)` 后看 `bot.pending`（`Packet.name` / `Packet.msg`）。
需要构造复杂请求时用 `bot.registry.message_cls(...)` 取当前 profile 的类，字段名与 handler 一致
（4.8 的改名由 `proto/4.7.51/field_map.json` 抹平）。

### 2.2 它刻意不做什么

- **不模拟客户端解码**：Bot 用和服务端同一份 schema，所以“服务端字段名写错、客户端才炸”这类
  问题它看不出来（4.8 的 `slot→slot_id` 就是这种）。这类问题要靠真机日志或抓包回放。
- **不测渲染**：黑屏、模型缺失、UI 错位，只能 L3。
- **不替代压力测试**：单会话串行，没有移动包洪峰。

## 3. L3：真机也别靠人手点（现成通道）

真机脚本 `scripts/game_test.ps1` 只负责起环境、截图、收日志，**不点鼠标**。下面四条通道可以把
“人点”也省掉，按落地成本排序：

### 3.1 服务端直接把你送进战斗：`/debug/challenge` 与 `/debug/peak`

```powershell
# 列出本赛季 MOC 层与 challenge id（需要先登录进世界）
curl "http://127.0.0.1:21000/debug/challenge"
# 直接进某一层 arena；second=1 直接进下半（验证“下半战斗本身能不能打”）
curl "http://127.0.0.1:21000/debug/challenge?id=5512"
curl "http://127.0.0.1:21000/debug/challenge?id=5501&second=1"

# 异相仲裁（Peak）：列 11 个组；直接进某一关 / BOSS 困难模式
curl "http://127.0.0.1:21000/debug/peak"
curl "http://127.0.0.1:21000/debug/peak?id=101"
curl "http://127.0.0.1:21000/debug/peak?id=104&hard=1"
```

`game_test.ps1 -Scenario peak -DebugPeak 101` 就是“登录后自动打这一发”，
配合事件截图可以把 Peak 的战斗侧取证也变成服务端可控路径（面板仍然要人点）。

大厅传送/点水晶/编队这三步最容易卡（`MapNPC:227-400001` 那条），这个入口直接跳过它们。
配合 `game_test.ps1` 的事件截图，就能做到“脚本开打、脚本拍黑屏、脚本收日志”。

### 3.2 任意包注入：`/debug/send`

```powershell
# 给当前会话推一个任意 cmd + body（body 为 hex）
curl "http://127.0.0.1:21000/debug/send?cmd=1434&hex=..."
```

`scripts/probe_cmd_ids.py` 已经用它反查命令号；同一入口也可以用来“制造客户端状态”
（推场景组、推 Notify），把需要点 UI 才出现的路径变成服务端可控路径。

### 3.3 客户端内 Lua：心跳通道

`PlayerHeartBeatScRsp.download_data` 会被客户端当 Lua 执行（见
[design/01 §3](../design/01-网络与登录.md)）。写法：

```powershell
.\.venv\Scripts\python.exe -m hsr.tools.lua_console push probe.lua   # 下一次心跳执行一次
.\.venv\Scripts\python.exe -m hsr.tools.lua_console status
```

已验证的是 `CS.UnityEngine.Debug.Log(...)` 这类（输出进 `Player.log`）。理论上可以调 `CS.RPG.Client.*`
直接驱动 UI，但**API 面还没探过**；要落地先做一次“列类型/列方法”的探针会话，别直接假设。

### 3.4 键盘注入（鼠标不行）

游戏是提权进程：普通权限下鼠标注入被 UIPI 拦（坑 5），键盘可用。所以真机自动化应尽量用
**键盘导航**（`F` 交互、`Esc` 返回、方向键选层、`Enter` 确认），不要写坐标点击；
必须点时，用 `/debug/*` 或 Lua 绕开。截图前记得 `SetProcessDPIAware()`（`game_test.ps1` 已处理）。

### 3.5 真机自动化的推荐落地顺序

1. 一条“进 MOC 并开打”的脚本：起服务端/代理/游戏 → 等登录 → `/debug/challenge` → 等 `SceneCastSkill`
   → 截图 → 断言 `Player.log` 无新异常 → 杀进程/还原代理；
2. 把“下半黑屏”做成固定场景：`second=1` + 事件截图（+0/+6/+14/+25 s）已经能取证；
3. 需要点菜单时再补键盘导航；Lua UI 驱动放到最后（收益最高、探索成本也最高）。

## 4. 抓包回放：把“人手跑一次”变成永久回归（下一步）

`tools/golden/4.6.54/` 已经有一份冻结的真实会话（499 帧，`capture.bin` + `sequence.json`）。
格式很简单：`[1B 方向][4B BE 长度][frame]`（见 `hsr/tools/decode.py`）。
设计中的 `scripts/replay_capture.py`：

1. 按 `sequence.json` 顺序取 C→S 帧，用 `bot.send_raw(cmd, body)` 原样发；
2. 每发一条，等对应 S 帧的命令号（超时 = 回归失败）；
3. 比对“是否有回包、retcode、body 大小档位”，不逐字节比（存档/时间戳本来就会变）；
4. 输出差异报告，失败时保留 `capture.bin` 片段 + 服务端日志。

这样“首登 259 个请求”只在升级客户端时抓一次，之后每个版本都能自动回归；
也能在 4.8 这种命令号整体重排时，快速列出“哪些请求开始没回包”。

## 5. 接进日常回归

- `scripts/check.ps1` 已加 `bot_smoke.py`（默认 profile）：单测 → proto → 离线回放 → **bot e2e** → 文档/ruff。
- 改 handler 时先跑 `bot_smoke.py --profile 4.6.54 --challenge --peak`（最全，30 步）；
- 改 4.7.51 字段映射时跑默认 profile，再看 `scripts/exercise_handlers.py`（填满字段）是否 31/31；
- 只有“必须看画面”的改动才开 `game_test.ps1`，并在报告里写明截图名。

## 6. 边界与坑

1. **单客户端**：bot 一握手会把当前游戏会话替换掉（`single_client`）。要么用独立端口/配置跑
   （`bot_smoke.py` 默认就是这么做的），要么先关游戏。
2. **心跳 15 s**：bot 每 4 s 自动发 `PlayerHeartBeatCsReq`；自己写长场景时别把 `pump` 停了。
3. **临时存档**：`bot_smoke.py` 用 `.tmp/bot-smoke/saves/`；不要在场景里直接写 `saves/player.json`。
4. **partial 表**：4.7.51 只有 140 条命令，缺的命令在 bot 里应报 `SKIP` 而不是 `FAIL`——
   那是“还没接”，不是“坏了”。
5. **服务端日志是证据**：失败时脚本自动打印 `.tmp/bot-smoke/server.log` 尾部；报告里贴这一段。
