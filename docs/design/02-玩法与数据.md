# design/02 · 玩法与数据

> **状态**：参考　**适用版本**：4.6.54（build 16927089）　**最后修订**：2026-11-10

这篇讲「哪些玩法需要服务端参与、参与到什么程度」，以及角色/阵容/场景/战斗/数据/存档的字段。
终局挑战单独在 [03-终局玩法](03-终局玩法.md)；网络层见
[01-网络与登录](01-网络与登录.md)。

> 结论先行：**星铁私服是“状态提供者”，不是模拟器**。战斗、移动、UI 状态大多由客户端计算，
> 服务端只负责给出合法的初始快照、接受结果、维护存档。

---

## 1. 心智模型

```text
客户端                          服务端
  │  请求初始状态（Get*Data）  →  从存档/资源表构造 protobuf
  │  ← 状态快照
  │  本地模拟（移动/战斗/UI）
  │  上报结果（PVEBattleResult）→  记录/丢弃，回执
  │  心跳（5s）                →  回时间 + 可选 Lua 脚本
```

三条设计原则：

1. **不要写战斗引擎**：让 `SceneBattleInfo` 每个字段自洽，客户端会自己打完；
2. **状态要能全量重发**：断线/切场景/换阵容时客户端会重新要数据；
3. **允许“假装”**：任务全完成、活动回空、好友列表为空、地图只放一个 calyx，客户端都能接受。

## 4. 角色与命途

### 4.1 两种数据

| 消息 | 用途 | 关键字段 |
|---|---|---|
| `Avatar` | 角色列表项（每个基座一条） | `base_avatar_id`, `level`, `promotion`, `equipment_unique_id`, `cur_multi_path_avatar_type`, `first_met_time_stamp`, `has_taken_promotion_reward_list` |
| `AvatarPathData` | 命途/技能树/遗器/星魂（每个形态一条） | `avatar_id`, `rank`, `avatar_path_skill_tree[]`, `equip_relic_list[]`, `path_equipment_id`, `ExRankList[]`, `dressed_skin_id`, `unk_enhanced_id` |

`GetAvatarDataScRsp` 还需：

```text
is_get_all = true
basic_type_id_list = [1001, 8001]   # 告诉客户端“这两个是多命途基座”
```

**没有 `basic_type_id_list`，主角/三月七的命途切换 UI 不出现。**

### 4.2 多命途映射

| 角色 | 基座 | 形态 id |
|---|---|---|
| 开拓者 | 8001 | 8001..8010（奇=男，偶=女；毁灭/存护/同谐/记忆/欢愉） |
| 三月七 | 1001 | 1001 存护 / 1224 巡猎 |

```python
def base_id(aid):
    if aid == 1224: return 1001
    if 8001 <= aid <= 8010: return 8001   # 不要写 aid > 8000
    return aid

# Avatar.base_avatar_id = base_id
# Avatar.cur_multi_path_avatar_type = 当前形态（由存档/性别决定）
# AvatarPathData.avatar_id = 形态 id
```

> 坑：早期把 `aid > 8000` 全映射到 8001，连 9000 段/非法 id 也会被当成主角；
> 必须限定 `8001..8010`，三月七只认 `1001/1224`。

### 4.2.1 命途切换请求

| 请求 | cmd | 作用 |
|---|---|---|
| `SetAvatarPathCsReq` | 343 | 切单个角色（`avatar_id` 是形态 id） |
| `SetMultipleAvatarPathsCsReq` | 320 | 一次切多个 |
| `UnlockAvatarPathCsReq` | 329 | 解锁命途；已有全部形态时直接 ack |

处理顺序（pearl 做法，本项目已复现）：

```text
校验形态存在且与 player.gender 同性别
→ 写存档（tb_multi_path / march_multi_path）
→ AvatarPathChangedNotify(base_avatar_id, cur_multi_path_avatar_type)
→ PlayerSyncScNotify(avatar_sync=新的 AvatarSync)
→ SyncLineupNotify(lineup) + SceneGroupRefreshScNotify
→ SetAvatarPathScRsp(retcode=0)
```

关键点：

- `AvatarPathChangedNotify.base_avatar_id` 是**基座**（8001/1001），
  `cur_multi_path_avatar_type` 是**形态**（8003/1224）；
- `GetAvatarDataScRsp.avatar_path_data_info_list` 只下发与 `player.gender` 同性的
  `8001..8010`；不要男女两套全发，否则命途 UI 状态会乱；
- `player.gender` 是权威开关（1 男 / 2 女）；`tb_multi_path` 不一致时自动校正；
- `PlayerSyncScNotify.avatar_sync` 要带完整 `avatar_list + path_data`；
- 队伍里的 `LineupAvatar.id` 用**当前形态**，存档内部仍存基座。

### 4.2.2 战斗侧映射

战斗里再映射一次：基座 `8001` → 当前命途形态，`1001` → 三月七当前形态。
`BattleAvatar.id` 用形态 id；不能直接拿队伍里的基座 id。

### 4.3 皮肤、强化、Ex 星魂

- 皮肤：
  - `GetAvatarDataScRsp.skin_list` 下发全部已拥有皮肤 id；
  - `DressAvatarSkinCsReq` (357) → 校验 `skin_id` 属于该角色 → 存档（按基座 id）
    → 推 `PlayerSyncScNotify(avatar_sync)`；
  - `TakeOffAvatarSkinCsReq` (315) → 写 0/删除；
  - 客户端从 `AvatarPathData.dressed_skin_id` 读当前皮肤；
  - 皮肤 id 与角色的对应在 `data/skins.json`；空 `skin_list` 会让皮肤页没有条目。
- 强化（`enhanced_id`）：`SetAvatarEnhancedIdCsReq`；`AvatarPathData.unk_enhanced_id`
  与 `BattleAvatar.enhanced_id`。
- Ex 星魂：`AvatarPathData.ExRankList` 与 `BattleAvatar.ex_rank_list`，值来自配置表。
  这是私服“超模”玩法来源，不是官方字段语义。

### 4.4 技能树

- `AvatarPathData.avatar_path_skill_tree[]`：`point_id`（锚点 1..18）+ `level`。
- `BattleAvatar.skilltree_list[]`：技能 id（`100101` 这类）+ 等级。
- 两套不是同一套 id，**不能混**。全 1 级/全满级都能跑；
  **关键是不要发空列表**，否则客户端可能按 0 级算。

### 4.5 全量同步顺序

`PlayerSyncScNotify` 一次只带一部分字段，客户端按到达顺序合并：

```text
1) del_relic_list / del_equipment_list     # 只发新旧差集
2) PlayerSyncScNotify(relic_list)
3) PlayerSyncScNotify(equipment_list)
4) PlayerSyncScNotify(avatar_sync)
5) 阵容变化时 SyncLineupNotify + SceneGroupRefreshScNotify
```

freesr 热更新沿用这个顺序（见 [../guide/03-交接与排障](../guide/03-交接与排障.md) §3 第 16 条）。

## 5. 阵容

### 5.1 `LineupInfo`

```text
name: "Squad 1"
mp: 5, max_mp: 5
leader_slot: 0
index: 0
plane_id: 0
is_virtual: false
extra_lineup_type: LineupNone
avatar_list {
  id: 1505, slot: 0, hp: 10000, satiety: 100,
  sp_bar { cur_sp: 10000, max_sp: 10000 },
  avatar_type: AvatarFormalType
}
```

- 队伍最多 4 人，slot 0..3；
- `hp/satiety/sp` 是展示值，给 10000/100/10000 即可；
- **`LineupAvatar.id` 是多命途形态 id**：主角用 `8001..8010` 当前形态，三月七用
  `1001/1224`。服务端内部可以存基座，但下发前必须映射，否则主角在队时换人失败。

### 5.2 会改阵容的请求

`JoinLineupCsReq`(705)、`ReplaceLineupCsReq`(782)、`QuitLineupCsReq`(759)、
`ChangeLineupLeaderCsReq`(798)。

```text
改存档 lineup
→ 发 SceneGroupRefreshScNotify（group 0，重新加载角色实体）
→ 发 SyncLineupNotify（新的 LineupInfo）
→ 发 XxxScRsp
```

`SceneGroupRefreshScNotify` 关键字段：

```text
floor_id: plane_id*1000 + 1
group_refresh_list {
  group_id: 0, state: 0, refresh_type: LOADED
  refresh_entity { add_entity { actor { base_avatar_id, avatar_type, uid }, entity_id: slot+1 } }
}
```

主角在队时：

- `ReplaceLineupCsReq.lineup_slot_list[].id` 可能是基座也可能是形态；
  统一 `base_id()` 归一化后再存；
- 下发 `LineupAvatar.id` 用当前形态（`Roster.lineup_id()`）；
- 先刷新场景实体，再发 `SyncLineupNotify`。

### 5.3 `GetLineupAvatarDataCsReq`（752，队伍 HP 表）

客户端在**进战前**问一次（实测时序：`SetClientPaused` → 752 → `StartCocoonStage`），用来画队伍血条。

```text
GetLineupAvatarDataScRsp {
  avatar_data_list { id: 8002, hp: 10000, avatar_type: AvatarFormalType }
}
```

- 响应**没有 slot 字段**，是“id → HP”的查表；多发无害，少发可能按默认值画；
- 两套 id 都发：基座（`Roster.forms`）+ 队伍形态（`Roster.lineup_id()`）；
- `hp` 恒等于 10000（`lineup_service.FULL_HP`），与 `LineupInfo.avatar_list[].hp` 一致；
- 不发也不会卡（`unknown_mode=empty_rsp` 兜底），价值是血条有数据 + 日志少一条 unhandled。

## 6. 场景

### 6.1 最小可用场景

```text
SceneInfo {
  plane_id: 20313
  floor_id: 20313001
  entry_id: 2031301
  game_mode_type: 1
  leader_entity_id: 1
  scene_identifier { floor_id: 20313001 }
  entity_group_list {
    # 组 0：角色
    entity_list { entity_id: 1
      actor { base_avatar_id: 1505, avatar_type: FORMAL, uid: 10001 }
      motion { pos_index { x: 31440, y: 192820, z: 433790 }, rot_index {} } }
    ... 每个 slot 一个 ...
  }
  entity_group_list {
    # 凝滞虚影（可交互物）
    group_id: 186
    state: 1
    entity_list { entity_id: 1337, group_id: 186, inst_id: 300001,
      prop { prop_id: 808, prop_state: 1 },
      motion { pos_index { x, y, z }, rot_index {} } }
  }
}
```

坐标是游戏内整数单位（不是米）。客户端不校验坐标，但放太远会掉出地图。

### 6.2 数据驱动场景（挑战）

`data/endgame.json` 里每个挑战带 `MapEntrance → PlaneID/FloorID`、
`MazeGroup → 场景实体组`、`Anchor → 出生点`、props/monsters 坐标。
`scene.build_challenge_scene` 用它生成 `SceneInfo`：

- 出生点优先 Anchor；缺 Anchor 时退到该组第一只 NPC 坐标，再退原点；
- `SceneState` 增加 `game_mode_type/world_id/saved_data`；普通 `build_scene` 不受影响；
- 地图信息 `GetSceneMapInfoScRsp`：`unlocked_teleport_list`、`maze_prop_list`、
  `maze_group_list`、`lighten_section_list`。

### 6.3 场景切换与移动

- `EnterSceneCsReq` → `EnterSceneScRsp`（回 `scene_identifier`、`is_over_map`）+
  `EnterSceneByServerScNotify`（新 `SceneInfo` + `LineupInfo` + `EnterSceneReason`）。
  顺序同 pearl；挑战“传送”就是走这条。
- 挑战结束/退出：`QuitBattleScNotify` + `EnterSceneByServerScNotify` 回原场景。
- `SceneEntityMoveCsReq` 可以完全忽略；要记录位置就回
  `SceneEntityMoveScRsp` 并把 `entity_motion_list` 原样带回。
  本项目记录领队位置，移动是客户端权威。

### 6.4 秘技（1498 / 1448）

实测时序：`1498` → 0.9s → `SceneCastSkillCsReq`(1405)，即“先请服务端扣点，再真正施放”。

- 协议里没有“点数”回包字段（`SceneCastSkillCostMpScRsp` 只有 `retcode/cast_entity_id`），
  **客户端自己在发包前就扣掉了**；服务端不补点，客户端会扣到 0 然后拒绝再放。
- 补点的坑：`SceneCastSkillMpUpdateScNotify`(1448) **只能“扣”不能“加”**——
  推 `mp=5` 客户端直接忽略（真机 A/B 验证）。唯一有效方式是 `SyncLineupNotify`
  重发整份 `LineupInfo`（含 `mp`），丹恒的 `LineupManager.GainMp()` 也这么做。
- 点数的载体是 `LineupInfo.mp / max_mp`（不是角色 MP；有 slot 的 `sp_bar` 才是战斗内 SP）。
- 策略在 `config.toml [gameplay].technique_points`：`unlimited`（默认，不消耗，每次放完刷满）/
  `refill`（心跳驱动，每 N 秒 +1）/ `on_empty`（扣到 0 立刻回满）/ `normal`（真机行为）。
  `unlimited` 每次施放多一条 `SyncLineupNotify`（约 60 字节），这是“不消耗”的代价。

### 7.1 触发点

| 请求 | 响应 | 场景 |

| `QuickStartCocoonStageCsReq` | `...ScRsp` | 快速开始 |
| `SceneCastSkillCsReq` 1405 | `SceneCastSkillScRsp` 1471 | 大世界打怪/挑战 |
| `StartQuickFarmElementCsReq` 1359 | `StartQuickFarmElementRsp` 1318 | 历战余响「快速挑战」 |
| `GetFarmStageGachaInfoCsReq` 1331 | `GetFarmStageGachaInfoScRsp` 1387 | 历战余响本周奖励 |

历战余响要点：

- 4.6.54 字段名被混淆：`StartQuickFarmElementCsReq{world_level=3, PAOFHFLFFHD=5, HECCOBFBJFI=15}`，
  其中 **`PAOFHFLFFHD` 是 farm element id**；`HECCOBFBJFI` 在 `ActiveFarmElementCsReq`
  里也出现，暂记日志。
- 真实 `FarmElementConfig.json` 以 `(ID, WorldLevel)` 映射 `StageID`；
  本项目在 `data/battle.json.farm_element_stage_map` 放扁平映射（真机日志补录），
  未登记就落 `farm_element_default_stage` 并告警。
- `GetFarmStageGachaInfoScRsp` 给每个 id 一个“未结束”的时间窗（本项目用一周）；
- 扫荡没有掉落管线，回 `retcode=0` + 空 `ItemList`。

### 7.2 `SceneBattleInfo` 字段

必填（缺了会闪退/软锁）：

```text
battle_id = 1
world_level = 6
stage_id = <关卡 id>
rounds_limit = <轮次上限，PF=4 / 其它 30>
logic_random_seed = <随机 uint32，或 time/5>
monster_wave_list[]              # 每波：battle_wave_id, monster_param.level, monster_list[]
battle_avatar_list[]             # 见 7.3
buff_list[]                      # 见 7.4
battle_target_info{}             # PF/AS 必须，见 7.5
```

可选：`battle_event`、`battle_rogue_magic_info` 等，先不填。

> `SceneBattleInfo` 字段 7 在 4.6.54 proto 里叫 `JAOIOKBBMFC`（uint32），
> pearl 规范化叫 `monster_wave_length`；填 0 或不填都不影响战斗。

### 7.3 `BattleAvatar`

```text
index: 0..3                       # 队伍槽位，不是角色 id
avatar_type: AvatarFormalType
id: <形态 id>
level, promotion, rank
enhanced_id
ExRankList[]
skilltree_list[] { point_id, level }
equipment_list[] { id, level, promotion, rank }
relic_list[] { id, level, main_affix_id, unique_id, sub_affix_list[] }
hp = 10000
sp_bar { cur_sp, max_sp }
world_level = 6
```

坑：

- `skilltree_list` 用技能 id（`100101`），`AvatarPathData` 用锚点 id（`1..18`），不能混；
- `relic_list.unique_id` 要和背包一致（战斗侧 `internal_uid`，背包侧 `1+internal_uid`）；
- 没有遗器时可以发空列表，但推荐发一个占位遗器，避免某些 UI 分支。

### 7.4 `BattleBuff`

```text
BattleBuff {
  id, level
  owner_index         # 角色槽位；0xFFFFFFFF = 全局
  wave_flag           # 0xFFFFFFFF = 所有波次
  target_index_list[]
  dynamic_values { "SkillIndex": float, "#ADF_1": float, ... }
}
```

常见魔法 id：

| id | 含义 | 来源 |
|---|---|---|
| `1000111..1000117` | 七属性弱点攻击 | echium `weakness_buff_id` |
| `1000119` | 无视弱点削韧 | 秘技 |
| `1000121` | 领队/全局支援 | 多个角色秘技 |
| `122401/122402/122403` | 三月七·巡猎 | 硬编码 |
| `140703` | Castorice 全局被动 | 私服开关 |
| `150602` | Silver Wolf 999 全局 | 私服开关 |
| `3034013` | 支援 buff | ppSR/pearl |

秘技通用规则：`id = avatar_id * 100 + 1`，`owner_index = 槽位`，
`dynamic_values["SkillIndex"] = 0`。祝福 `owner_index=0xFFFFFFFF`，`level` 来自配置。

### 7.5 关卡目标（PF / AS）

```python
# 虚构叙事（PF）
battle_target_info[1] = { id: 10003 if stage_id >= 30309011 else 10002, progress: 0 }
battle_target_info[2..4] = {}          # 占位，key 必须存在
battle_target_info[5] = { [id:2001, id:2002] }

# 末日幻影（AS）
battle_target_info[1] = { id: 90005, progress: 0 }
```

pearl 还填 `total_progress`（80000）和 `progress`（首节点 0 / 第二节点 40000），
AS `progress=2000`；这些影响 UI 进度条，不影响战斗。

### 7.6 战斗结果与「再来一次」

```text
PVEBattleResultCsReq → PVEBattleResultScRsp {
  end_status = req.end_status
  battle_id = req.battle_id
  stage_id = req.stage_id
}
```

客户端自己结算奖励/星数，服务端只回执。**「再来一次」的关键**：每次
`StartCocoonStage` 必须分配**新的 `battle_id`**；一直回同一个 id 会让客户端停在结算页。

```python
battle_id = seed if session.battle_seq == 0 else session.battle_seq + 1
session.battle_seq = battle_id
```

边界规则：

- `BATTLE_END_WIN/LOSE/QUIT` 都清 active battle；
- 晚到的 `battle_id` 不匹配时只 warning，不清当前新战斗；
- `QuitBattleCsReq` 也清 active；
- `QuickStartCocoonStage` 与 `Start` 共用同一套 id/active 逻辑。

### 7.7 常见失败模式

| 现象 | 原因 |
|---|---|
| 进战斗黑屏/闪退 | `battle_avatar_list` 为空、`stage_id` 找不到、`monster_wave_list` 为空 |
| 角色 0 血/技能 0 级 | `skilltree_list` 空、`level/promotion` 为 0 |
| 伤害异常/没有弱点 | 弱点 buff 的 `owner_index` 或 `id` 错 |
| 战斗结束卡住 | 没回 `PVEBattleResultScRsp`，或 `battle_id` 不匹配 |
| 结算页「再来一次」没反应 | 每次 Start 复用旧 `battle_id`；必须每场递增 |
| PF 没有进度条 | `battle_target_info` 缺 key 1/5 |
| 秘技不生效 | `dynamic_values` 缺 `SkillIndex`，或 `wave_flag` 不是 `0xFFFFFFFF` |

## 12. 数据与存档

### 12.1 `freesr-data.json`

```jsonc
{
  "key": "default",
  "avatars": {
    "1001": {
      "avatar_id": 1001,
      "data": {
        "rank": 0,
        "skills": { "100101": 1 },
        "skills_by_anchor_type": { "1": 1, "18": 1 },
        "ex_rank_id_list": [120401]
      },
      "level": 80, "promotion": 6, "sp_value": 0, "sp_max": 100,
      "techniques": [100101], "enhanced_id": 0
    }
  },
  "relics": [{
    "internal_uid": 1, "equip_avatar": 1001, "level": 15,
    "main_affix_id": 1, "relic_id": 61321, "relic_set_id": 132,
    "sub_affixes": [{ "count": 1, "step": 2, "sub_affix_id": 4 }]
  }],
  "lightcones": [{
    "internal_uid": 0, "equip_avatar": 1001, "item_id": 24005,
    "level": 80, "promotion": 6, "rank": 5
  }],
  "battle_config": { "battle_type": "MOC", "stage_id": 30123122, "monsters": [] }
}
```

语义：

- `avatars` 的 key 是**字符串**；程序内部 `int(k)` 或统一 str；
- 多命途会同时存在多个形态（`8001..8010`、`1001/1224`），下发前按 §4 折叠；
- `techniques` 是**秘技 id**，不是技能树 id；
- `relic_id % 10` = 部位；`count/step` 原样透传到 `RelicAffix{cnt, step, affix_id}`；
- `battle_config` 只落盘，**不参与战斗**。

### 12.2 热更新

入口：

| 入口 | 说明 |
|---|---|
| `POST /srtools` | SR Tools 网页「连接设置 → RobinSR → 连接 PS」；无 `data` 的探活请求回 200 不改数据 |
| `GET /srtools` | 在线状态（avatars/relics/lightcones/sessions/hot_reload） |
| `GET /srtools/export` | 下载当前 freesr 文件（网页「加载数据」用） |
| `POST /admin/freesr/reload` | 手动覆盖文件后立刻重载 |
| 文件 mtime 监视 | `features.freesr_watch`，默认 2 秒，覆盖文件即生效 |

一次热更新：校验 → （网页推送时）防误清空 → 原子写回 → 替换 roster →
重算在线 session 形态/阵容 → 推送（删旧 id → 遗器 → 光锥 → avatar_sync → 必要时阵容）。

- 防误清空：网页没“加载数据”时推空遗器/光锥会被 400 拒绝；`?force=1` 可强制；
- `multi_path` 会切主角/三月七形态；`lua` 忽略；`battle_config` 只落盘；
- 文件用 `utf-8-sig` 读（网页导出可能带 BOM）。

### 12.3 玩家存档

`player.json`：

```json
{
  "schema": 1,
  "lineup": [1501, 1513, 1511, 1506],
  "leader": 2,
  "tb_multi_path": 8010,
  "march_multi_path": 1001,
  "skins": {"1505": 1150501, "1001": 1100101},
  "plane_id": 20313,
  "pos": [31440, 192820, 433790],
  "finished_tutorials": [],
  "finished_guides": [1101, 1102]
}
```

- 阵容/命途/皮肤**按基座 id 存**，发协议时映射成当前形态；
- `pos` 只在 `world.persist_position=true` 时恢复；
- `finished_tutorials/guides` 只记录客户端额外确认的 id；`data/tutorials.json` 仍下发全完成。

写入：

- 原子写（`tmp` + `Path.replace()`）；
- 默认 5 秒节流；阵容/命途/皮肤 `force=True` 立即写；坐标走节流；
- 只写“重启后必须一样”的东西：`battle_id`、秘技点、section、active battle/challenge
  都是会话级，不落盘；
- 目前没有 `.bak` / schema 迁移链；改字段时在 `PlayerSave.from_dict()` 给默认值，
  必要时递增 `schema`。

### 12.4 UID / unique_id

| 对象 | 当前做法 | 说明 |
|---|---|---|
| 玩家 uid | `config.toml [player].uid`，默认 10001 | 客户端只用于显示/关联 |
| 遗器 unique_id | `1 + internal_uid` | `roster.py::relic_uid` |
| 光锥 unique_id | `2000 + internal_uid` | `lightcone_uid`，与遗器区间错开 |
| 角色实体 entity_id | 1..4（队伍槽位） | 客户端按槽位找 |
| 场景实体 entity_id | 1000+ | 挑战/场景实体 |
| 怪物 entity_id | 100000+ | 挑战场景沿用 pearl 约定 |

协议只要求 `unique_id` 唯一且稳定；不要每次启动重算，否则客户端缓存会错乱。
