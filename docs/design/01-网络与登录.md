# design/01 · 网络与登录

> **状态**：参考　**适用版本**：4.6.54（build 16927089）/ 4.7.0（build 17108910）　**最后修订**：2026-11-12

这篇讲「客户端从双击到进入游戏」这条链：HTTP 登录、UDP 握手、KCP、帧、心跳，
以及协议层（proto/CmdId/代码生成/命名坑）。
玩法字段见 [02-玩法与数据](02-玩法与数据.md)，抓包基线见
[../reference/01-登录序列与基线](../reference/01-登录序列与基线.md)。

---

## 1. 总链路

```text
StarRail.exe
   │
   ├─(1) HTTPS  query_dispatch / SDK JSON   ──被代理劫持──> 127.0.0.1:21000  (HTTP)
   │                                                          │
   ├─(2) HTTPS  query_gateway (base64 protobuf) ──────────────┘
   │         └─ 返回 ip=127.0.0.1, port=23301 + 热更资源地址
   │
   └─(3) UDP   23301  20B 握手 → KCP → 帧(cmd+protobuf)
```

- 第 1、2 步是 HTTP(S)，由**代理**把 `*.starrails.com` / `*.bhsr.com` / `*.mihoyo.com`
  等域名改写到本机。服务端假设“代理已经装好”，自己不处理 TLS。
- 第 3 步是裸 UDP，不加密。
- 客户端会先发 `HEAD /query_gateway` 探活；**405/404 会直接中断登录**。
- `query_gateway` 之后、连游戏服之前还有一步**资源校验**：客户端按 hotfix 给的 CDN 地址取资源清单，
  版本对不上就下载。CN PROD 客户端（4.7.0）同样如此，绕过办法见
  [../reference/05-4.7.0兼容性实测](../reference/05-4.7.0兼容性实测.md) §3。
- 4.6.54 还会在 `query_gateway` 之后调用
  `POST /account/ma-cn-session/app/exchange`；**404 会拿不到 session token，卡在连游戏服之前**。

## 2. HTTP 接口清单

### 2.1 两个 protobuf 接口

| 方法 | 路径 | 返回 | 说明 |
|---|---|---|---|
| GET | `/query_dispatch` | `base64(Dispatch)` | 区域列表；`region_list[0].dispatch_url` 决定下一次请求发到哪 |
| GET/HEAD | `/query_gateway` | `base64(GateServer)` | 游戏服 ip/port + 热更 CDN；HEAD 必须 200 |

`Dispatch` 最小可用字段：

```text
Dispatch {
  retcode = 0
  msg = "OK"
  top_server_region_name = "echium"
  region_list { name, title, display_name, env_type="9",
                dispatch_url="http://127.0.0.1:21000/query_gateway" }
}
```

`GateServer` 最小可用字段：

```text
GateServer {
  ip = "127.0.0.1"
  port = 23301
  unk1..unk8 = true        # 4.6.5x 的 8 个未知 bool，全部 true 最宽松
  asset_bundle_url, asset_bundle_url_b(1379), ex_resource_url,
  lua_url, ifix_url, ifix_version(1286),
  lua_version(1516)
}
```

> 字段号有版本漂移：4.6.53 里 1379 叫 `asset_bundle_url_android`、1516 叫
> `mdk_res_version`；4.6.54 里叫 `asset_bundle_url_b` / `lua_version`。
> **线格式只认字段号，不认名字**。本项目用 `versions/4.6.54.toml [field_aliases]` 抹平。

### 2.2 JSON 接口（14 个左右）

| 路径 | 作用 | 最低要求 |
|---|---|---|
| `POST /hkrpg_{region}/mdk/shield/api/login` | 账号登录 | `retcode=0` + `data.account.{uid,token,area_code,country,email,is_email_verify}` |
| `POST /hkrpg_{region}/mdk/shield/api/verify` | 账号校验 | 同上 |
| `GET /hkrpg_{region}/combo/granter/api/getConfig` | SDK 配置 | `data.protocol=true` 等 |
| `POST /hkrpg_{region}/combo/granter/api/compareProtocolVersion` | 协议版本 | `data.protocol_version=""` |
| `POST /hkrpg_{region}/combo/granter/login/v2/login` | 换 combo_token | `data.{account_type,combo_id,combo_token,data:"{\"guest\":false}",heartbeat:false,open_id}` |
| `POST /account/ma-cn-passport/app/loginByPassword` | 账号密码登录 | `data.token.token` + `data.user_info` |
| `POST /account/ma-cn-session/app/verify` | 校验 token | `data.tokens[].token` |
| `POST /account/ma-cn-session/app/getTokenByGameToken` | 换游戏 token | `data.{uid,token.token,game_token}` |
| `POST /account/ma-cn-session/app/exchange` | **4.6.54 新增** | `data.{uid,token,session_key,game_token,...}` |
| `POST /account/risky/api/check` | 风控 | `data.action="ACTION_NONE"` |
| `POST /hkrpg_{region}/combo/red_dot/list` | 小红点 | `data:{}` |
| `GET /hkrpg_{region}/mdk/shield/api/loadConfig` | 防作弊配置 | `data.id/game_key/client/identity` |

关键点：

1. **token 贯穿两条协议**：`getTokenByGameToken` 返回的 `data.token` → 客户端在游戏服
   第一帧 `PlayerGetTokenCsReq` 的字段 5 原样带回。服务端不校验，但工具链可以用它关联账号。
2. **region 是路径变量**：`/hkrpg_cn/...` 和 `/hkrpg_global/...` 都要命中，用同一个 handler。
3. 返回值必须是 JSON 字符串（`json.dumps`），不是 `text/plain` 包 JSON。
4. 客户端对未实现的接口**大多能容忍 404**，但 `query_gateway` / `exchange` 不能。

### 2.3 hotfix

`query_gateway` 里必须回与客户端版本匹配的 CDN 地址；客户端会拿它去校验/下载
lua、ifix、assetbundle。版本 key 形如 `OSBETAWin4.6.54`（beta 通道）或 `CNPRODWin4.7.0`（CN 正式），
来自 `PlayerLoginCsReq` 字段 11，也是 `query_gateway` 的 query 参数。

- `data/hotfix.json` 按 build 查表；未知版本回退到最接近的已缓存版本；
- 离线时保留 hotfix，成本极低；返回空 URL 会让客户端重新校验资源；
- `versions/4.6.54.toml` 的 `hotfix_key` 与 `data/hotfix.json` 的 key 必须一致；
- 客户端比对的是**安装时那份清单**：URL 里的 `output_<id>_<hash>` 与本地索引不一致就会下载。
  社区没有对应条目时，可用“本地清单回放”把客户端自己的清单回给它，见
  [../reference/05-4.7.0兼容性实测](../reference/05-4.7.0兼容性实测.md) §3。
- 本地回放的实现（4.7.0 起）：`data/hotfix.json` 的条目用 `LOCAL_CDN/<kind>/Live/output_...`
  占位，`features.local_cdn` 打开时换成 `http://<listen>:<http_port>/cdn/...`；`/cdn/**` 由
  `hsr/dispatch/local_cdn.py` 按 basename 回放客户端 `StarRail_Data/{Persistent,StreamingAssets}`。
  其中 `M_Design_ArchiveV` 在运行时改写 ContentHash/FileSize，指向 `Persistent` 里真实的
  `DesignV_*.bytes`（`StreamingAssets` 里那份是 1.3 KB 安装期 stub，会让客户端 textmap NRE）。
  清单必须保持客户端自己的格式：**一行一个 JSON + CRLF**；用 `..` 拼一行能过预登录校验，
  但进世界前的版本更新会严格解析整份文件并失败，弹「任务资源管理」全量下载
  （[../reference/05-4.7.0兼容性实测](../reference/05-4.7.0兼容性实测.md) §3.1）。
  回放只读，客户端自己写 `*_cache.bytes` 属正常行为。
- 本地缺条目时，可开 `features.hotfix_auto` 向官方网关取一次（默认关闭）：`hsr/dispatch/official.py` 只 `GET query_gateway`、复用客户端
  参数、直连绕本机代理、5 s 超时，成功写回 `data/hotfix.json`，失败静默回退本地表——
  与参考工程 sr-recover-new 的 `check_hotfix` 思路一致。

## 3. 游戏服传输

### 3.1 20 字节握手

客户端连上 UDP 23301 后先发一个 **固定 20 字节**的握手包：

```text
偏移 0   4B  code       255 = CONNECT，404 = DISCONNECT（大端；字节为 00 00 00 ff）
偏移 4   8B  保留
偏移 12  4B  enet       （读了不用）
偏移 16  4B  尾部标记   ff ff ff ff
```

服务端回 20 字节：

```text
00 00 01 45 | conv/token 共 8B | 00 00 00 00 | 14 51 45 45
```

- `0x145` 和 `0x14514545` 是固定魔数；
- 中间 8 字节是会话标识（见 3.3）；
- 握手必须**先于任何 KCP 数据**；首个包在握手前不做业务。

### 3.2 游戏帧

```text
偏移 0   4B  魔数 9D 74 C7 14
偏移 4   2B  cmd      uint16 大端
偏移 6   2B  head_len uint16 大端
偏移 8   4B  body_len uint32 大端
偏移 12  nB  head
         mB  body     protobuf
末尾 4   4B  魔数 D7 A1 52 C8
```

- 总长 = `12 + head_len + body_len + 4`；
- **head 是客户端包序号**，protobuf 字段 1 varint，从 1 开始递增；服务端回包 head 恒为空；
- 服务端可以在一次 KCP 收包循环里连续回多个帧（通知类），客户端按 cmd 分发；
- 客户端对“没回包”的请求非常宽容：首登前 100 帧的 69 条 C→S 请求里，只处理约 19 条
  也能进游戏。

### 3.3 KCP：已判定为 `u32_le_token`

游戏用魔改 KCP：标准头 24 字节，这里 **28 字节**（多 4 字节 token）。
两套参考实现对这 8 字节的解释不同，**2026-11-09 已用真实 4.6.54 流量判定**：

```text
u32 conv   (LE)
u32 token  (LE)     <-- 多出来的 4 字节
u8  cmd
u8  frg
u16 wnd    (LE)
u32 ts, sn, una, len (LE)
```

- 握手响应：`conv`、`token` 各按**大端** 4 字节写；
- KCP 段里：`conv`、`token` 各按**小端** 4 字节写；
- 判定证据：握手响应 blob `45 26 35 2a 07 ab d2 74`，客户端首个 KCP 包的 conv 字段是
  `2a 35 26 45 74 d2 ab 07` —— 即 **LE(conv32) || LE(token32)**；
- 服务端默认 `config.toml [server].kcp_conv_mode = "u32_le_token"`；
  `u64_be` 只作为其他 build 的实验选项保留。

KCP 参数：

| 参数 | 本项目 | 说明 |
|---|---|---|
| MTU | 1400 | MSS = 1372 |
| nodelay | 1,10,2,1 | 快速模式 |
| wnd | 256/256 | 窗口放大更抗丢包 |
| overhead | 28 | 魔改头 |

### 3.4 心跳与超时

- 客户端约 **5 秒**一次 `PlayerHeartBeatCsReq`（cmd 45）→ `PlayerHeartBeatScRsp`（cmd 16）；
- 服务端把 `client_time_ms` 原样回填，并给 `server_time_ms`；
- `heartbeat_timeout = 15.0`：15 秒无包断会话；
- 心跳响应还带 `ClientDownloadData`（version=51, time, data），这是**给客户端注入 Lua 的通道**：
  `lua/main.lua` 里的 `-- exec=tt`（一次）/`tf`（每次）会被下发；脚本输出到 `Player.log`。

## 4. 协议层

### 4.1 资产

| 资产 | 位置 | 说明 |
|---|---|---|
| `StarRail.proto` | `proto/StarRail.proto` | 768 KB，4,930 message / 473 enum，单文件无 package |
| `CmdId.json` | `proto/CmdId.json` | 2,621 条（949 CsReq / 939 ScRsp / 293 Notify） |
| `hsr.desc` | `proto/hsr.desc` | `FileDescriptorSet`，工具链动态解码用 |
| `build_info.json` | `proto/build_info.json` | proto 来源/生成信息 |
| `gen/` | `hsr/protocol/gen/` | `protoc` 生成物，**不要手改** |

两份参考 proto 命名风格不同（`DeployRotaterCsReq` vs `DeployRotatorCsReq`），不能混用。
本项目只用与 `CmdId.json` 同源的一份。

### 4.2 代码生成

选 **官方 protoc + protobuf 运行时**，不选 betterproto2：

| 方案 | 生成 | 导入 | 编解码 |
|---|---|---|---|
| betterproto2 | 单文件 91k 行 / 2.9 MB | 1.22 s | 纯 Python |
| protoc + protobuf | `StarRail_pb2.py` 1.8 MB | 0.08 s | C(upb) 微秒级 |
| 运行时动态 | 无 | 建池 18 ms | 首次建类 0.07 ms |

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\gen_proto.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\check_proto.py
```

`registry.py` 的关键规则：

```python
# 1. 名字查 id：优先精确匹配；失败则去掉尾部数字再试
# 2. id 查名字：用 dict[int, list[str]]，因为存在一 id 多名的脏数据
# 3. 消息类：name -> getattr(gen, name)；带数字后缀时 strip 后再取
# 4. 方向：CsReq/ScRsp/Notify 后缀 + 显式方向表（Notify 无 CsReq）
```

`codec.py`：`encode` / `decode(name, body)` / `decode_any(cmd, body)` / `dump` / `json`；
未知名字用动态池，坏数据回退 wire-type 启发式 dump。

### 4.3 覆盖策略

echium 的“30 handler + 31 dummy 就能进游戏”是历史结论，说明**首登链路只需很少 handler**。
本项目当前 74 个 handler（含场景/战斗/挑战/皮肤/档案）；数字见
[docs/README §3](../README.md#3-关键数字唯一事实源)。未知命令默认回空 `ScRsp`。

## 5. cmd id 不能跨版本复用

**同一个 build 内**（4.6.53 ↔ 4.6.54）可以复用一份表 + 少量改名补丁；
**换 build 必须重新提取 CmdId**，并**按命令名 + 消息字段签名对齐**，不能按 id 对齐。

真跨版本实测（2026-11-10，按名字对齐）：

| 对照 build | 同名命令数 | id 相同数 | 占比 |
|---|---:|---:|---:|
| pearl 快照（实为 4.6.54 导出） | 2,586 | 2,586 | 100% |
| echium（4.6.53/54） | 2,621 | 2,621 | 100% |
| Himeko-Nova-SR 4.5 | 2,012 | 10 | 0.5% |
| DanhengServer 3.7.0 | 1,724 | 8 | 0.5% |
| LunarCore 4.2.0 | 1,188 | 19 | 1.6% |
| qingque-sr | 1,632 | 23 | 1.4% |

例：`PlayerGetTokenCsReq` 在 4.6.54 是 `5`，Danheng 3.7 是 `83`、LunarCore 4.2 是 `14`、
Himeko 4.5 是 `44`。**cmd id 每个 build 都会整体重排。**

> 4.6.54 抓包唯一命令 212 个，本项目的表能查到 211 个；唯一缺失 `8541`
> （客户端发了但无影响，未知命令静默）。升级对照方法见
> [../reference/01-登录序列与基线](../reference/01-登录序列与基线.md) §5。

## 6. 命名坑（会直接导致 KeyError）

### 6.1 带数字后缀的别名

`CmdId.json` 里有一批名字以数字结尾，它们**不是 proto 消息名**：

```text
GetDataCsReq1         -> GetDataCsReq      (cmd 10235)
GetDataScRsp2         -> GetDataScRsp      (cmd 10228)
DoGachaScRsp1         -> DoGachaScRsp      (cmd 9418)
PickRogueAvatarCsReq1 -> PickRogueAvatarCsReq (cmd 1848)
```

原因：不同版本/命名空间下有同名命令，导出时加后缀去重。
**注册表必须做“去掉尾部数字再找 message”的回退。**

### 6.2 重名/重号

- `GetMonopolyFriendRankingListCsReq` 和 `...ScRsp` **共用 cmd 7064**（表本身的 bug）。
  不要依赖“一个 cmd 唯一对应一个消息”，按方向区分。
- `PVEBattleResultCsReq` 这种全大写缩写，不要用“下划线转驼峰”去猜；
  handler 显式写 `router.add("PVEBattleResultCsReq", fn)`。

### 6.3 字段名

- 新内容的消息名/字段名大量混淆：`SceneBattleInfo.JAOIOKBBMFC = 7`、
  `AvatarPathData.ExRankList = 8`、`GetGachaInfoScRsp` 里也有 `CIKPBGDIABO` 之类。
- **`ExRankList` 这种大写字段**：官方 protoc **原样保留**，访问要写 `msg.ExRankList`。
- 字段号可以很大（`SceneBattleInfo` 最大到 2044，`GateServer` 到 1975），
  不要假设字段号 < 100。

## 7. 版本策略

- **锁定一个客户端 build**：4.6.54 / 16927089。proto、cmd 表、抓包、资源都按这个 build 存档。
- `versions/4.6.54.toml` 是 version/build/hotfix/proto 目录的权威源；
  `config.toml [server].profile` 选择它。
- proto 表**不要运行时从客户端动态生成**；构建期生成一次并提交 `hsr.desc` 与 `StarRail_pb2.py`。
- 升级：重新导出 proto/cmd → 生成 → 用旧抓包回放 → 看字段差异 → 只改业务层。
- 所有“按版本变化的常量”（字段号别名、cmd 表、hotfix key）集中放 profile，不散落在 handler。
- 完整升级流程见 [../reference/02-开发与版本更新](../reference/02-开发与版本更新.md) §6。
