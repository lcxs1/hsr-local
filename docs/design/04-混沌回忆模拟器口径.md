> **状态**：M1 已实现；4.6.54 真机 8 轮后确认下半黑屏/大厅卡死是客户端问题，**改用 4.7.0 继续**（见 §5.1）　**适用版本**：4.6.54（build 16927089）/ 4.7.0（build 17108910）　**最后修订**：2026-11-11

目标一句话：**忘却之庭 → 混沌回忆 → 12 层任意一层直接开打；每层分上下半，两套队伍，两场战斗，打完才结算。**

## 2. 现状（已核过的事实，不是猜测）

**数据层已够用**，缺的都在 UI 与两段式流程上：

- `data/endgame.json`：843 条（MOC 639 / PF 112 / AS 92），MOC 里 **629 条有 node2**（即上下半）。
- 混沌回忆是「一场景多楼层」：以当前赛季 group `1036`（物竞天择）为例，id `5501..5512` = 第 1..12 层，
  全部 `entrance=3013801 / plane=30138 / floor=30138001`，上半 `MazeGroupID1=4`、下半 `MazeGroupID2=5`。
  → **换层 = 换 challenge id**（同一场景），**换半 = 同场景内换实体组**。
- 已有实现：`hsr/game/services/endgame.py`（表）、`services/challenge.py`（状态/战斗包/`advance_stage`）、
  `handlers/challenge.py`（GetChallenge/StartChallenge/Settle/Leave）、`services/scene.py:452 build_challenge_scene`。
- 真机（`logs/test/test-20261111-181334.server.log`）：上半 id=15 打通；服务端 18:16:25 自动 `advance` →
  18:16:31 发下半 `SceneBattleInfo` → 18:16:47 客户端自己回 `WIN`，**画面是黑的**。

**两个具体缺陷（对得上参考实现）**：

1. `StartChallengeScRsp.lineup_list` 只回了**当前这一半**的一套阵容（`handlers/challenge.py:272`）。
   DanhengServer 与 LunarCore 在 `StageNum >= 2` 时**两套都回**。
2. 上半结束后是**重建整份 SceneInfo**再推给客户端（`services/challenge.py:277 advance_stage`）；
   参考实现是**原地卸载 group1、加载 group2**，再把当前这一套阵容切到 `LineupChallenge2`。

**卡片缺失的原因还没定死**（这是 §4.3 的探针任务）：

- 真机只出两张卡：`永屹之城遗秘 45/45`、`天瞳求仙迷航录 18/18`。
  45 = group `100`（15 层 × 3 星）、18 = group `900`（6 层 × 3 星）——即**我们发的 `star=7` 被按组汇总**了。
- 这两组在 `ChallengeMazeConfig` 里都**没有 `Floor` 字段**（常驻组）；带 `Floor` 的轮换组（1001–1037）一张卡都不出。
- 已知不是 `challenge_group_list` 驱动：发 109 个组仍只有 2 张卡（[03 §5](03-终局玩法.md)）。

## 3. 参考工程怎么做的（这次的依据）

| **Himeko-Nova-SR** | 同 pearl，另发 `max_level_list`（`level=12, reward_display_type=101212`），4.7 协议 | 同 pearl | 同 pearl |
| echium / qingque-sr | `GetChallenge` 空回或仅映射命令，可忽略 | — | — |

**两个决定性的共同点**（三家完整实现都这么做，我们两家都没做）：

1. `StartChallengeScRsp` 在 `StageNum >= 2` 时 `lineup_list` **两套都发**
   （`DanhengServer/.../PacketStartChallengeScRsp.cs:32-33`、`LunarCore/.../PacketStartChallengeScRsp.java:30-35`）。
2. 下半是**同场景换组**，不是换场景。

另：`StartChallengeCsReq` 一次就带两套阵容（真机日志 `first=[1505,1502,1414,8001] second=[1503,1506,1501,1511]`），
所以服务端在**上半开始时就该把两套都注册好**（Danheng `HandlerStartChallengeCsReq.cs:20-28` 就是这么做的），
不能等下半再想办法。

## 4. 设计

### 4.1 选关：三层，逐层兜底

- **L0 数据**：楼层清单来自 `data/endgame.json` 的某个 group；**选哪一组由时间决定**——用 `data/vendor/srtools-<日期>/endgame_index.json` 的 `BeginTime/EndTime` 取“当前赛季”，2026-11-11 是 `1036 物竞天择`（`5501..5512`），下一期才是 `1037 漆黑残响`；默认回落到最新期（12 层组）
  配置项 `[endgame] moc_group_id` 可换任意组（1001–1037 都是 10/12 层）。
- **L1 解锁**：12 层全部 `star=7` 下发（pearl 的写法，已验证客户端会显示为可打）；
  `GetChallenge` 里每层带 `taken_reward=42`。玩家想打第 12 层直接点。
- **L2 卡片**：补「物竞天择」（见 §4.3）。卡片没修好也不阻塞 L1/L3，只影响“看得见”。
- **L3 兜底（一定要做）**：聊天命令 `/moc <challenge_id>`（或 `/moc <floor>`）= pearl 的 custom mode。
  服务端记住 `session.pending_challenge_id`，下一次 `StartChallenge` 用它建战斗。
  这样即使卡片/楼层 UI 缺失，**任意关卡永远可打**，也是 A 口径的“逃生门”。

> 为什么不做「所有历史期都能选」：客户端楼层列表是它自己按**当前期**渲染的，
> 历史期不出现在 UI 里；服务端没法凭空造出旧期卡片。要跨期就用 L3 命令。

### 4.2 上下半：改成参考实现的“原地换组”

**StartChallenge（上半）**

1. 解析 `avatar_lineup_first` / `avatar_lineup_second`（现有逻辑，`handlers/challenge.py:197-238`）。
2. 两套都存进 `ChallengeState`（已有 `first_avatars` / `second_avatars`）。
3. 响应改成：`lineup_list=[Challenge 队, Challenge2 队]`（新增 `challenge_service.lineup_info(session, second=...)`），
   `cur_challenge.extra_lineup_type=LineupChallenge`。
4. 场景照旧 `build_challenge_scene(node1)`。

**上半 WIN → 下半（`handlers/battle.py:145` 那条分支）**

1. **不要**重建 SceneInfo。新增 `scene_service.swap_challenge_group(session, group_id)`：
   发 `SceneGroupRefreshScNotify` 先删 group1 实体（含那只 NPC 怪），再按 group2 数据加实体
   （对齐 Danheng `SceneEntityLoader.UnloadGroup/LoadGroup`，`:230-250`）。
2. `ChallengeLineupNotify(LineupChallenge2)` + `SyncLineupNotify(lineup=第二队)`。
3. `cur_challenge` 标记 stage=2（`ChallengeState.stage=2`，`extra_lineup_type=LineupChallenge2`）。
4. 若同一时刻客户端自己发了 `StartChallengeCsReq`（只带第二套，pearl 流程），
   现有分支保留：走同一个 `advance` 函数，幂等（已在 `:202-226`）。

**下半 WIN** → `ChallengeSettleNotify(FINISH, star)`；**LOSE** → `FAILED`；`LeaveChallenge` 回大厅（现有）。

**为什么必须换掉现在的重建场景**：客户端已经知道自己在哪个 arena 里，
再塞一份新的 `SceneInfo`（新 entry/新实体 id）会让它的战斗区域初始化和场景对不上——
现象正是“黑屏但战斗在跑（16 s 后自己结算）”。这是最像的一根因，先用 M1 验证。

**数据层还有一个坑（新数据才看出来）**：639 条 MOC 挑战里有 **130 条的上半是 2 个 stage**
（`EventList1` 两条，例如 `101` 上半 = 30001161「守护者之影」+ 30001162「蚕食者之影」），
我们和 pearl 现在都只取最后一条，等于**少打一场**。
M0 顺带看一眼：打赢第一场后客户端会不会接着要求下一场（继续 `SceneCastSkill`）；
会的话 M1 里把「一个半场多场战斗」按顺序串起来（同一场景换怪，不换队伍）。

### 4.3 「物竞天择」卡片：三个假设，按成本顺序试

每个假设单独一轮真机，只看“卡片是不是 3 张”，不做别的改动：

| # | 假设 | 改法（都在服务端） | 判据 |
|---|---|---|---|
| H1 | 客户端按**时间窗口**过滤轮换组，只有无 `Floor` 的常驻组 100/900 出卡 | 先核对“客户端自己的窗口”与“服务端报的时间”：`handlers/login.py:16` 的 `_now_ms()` 可加配置偏移（`[time] offset_days`），试落进 `1036 物竞天择` 的 11-02 ~ 12-14 | 卡片出现第三张 = 命中 |
| H2 | 卡片需要 `max_level_list` + 组统计（Himeko 发了 `max_level_list`，我们一条没发） | `GetChallengeScRsp.max_level_list` 补 `ChallengeHistoryMaxLevel(level=12, reward_display_type=…)`；`challenge_group_list` 只发真实领奖组（Danheng 写法） | 同上 |
| H3 | 大厅 100000104 的三块牌子道具缺一块（现有 13 个 prop 里只有 3 个像牌子：`100083 / 101028 / 100018`） | 对比 entry `1000001/2/3` 的组差异，把缺的 prop/group 补进 `data/endgame.json` 的 `lobby` 段 | 同上 |

> 2026-11-11 的新证据削弱了“赛季过期”这个说法：从 srtools 新数据看，`物竞天择 = group 1036`，
> 窗口正好是 **2026-11-02 ~ 2026-12-14**，今天（11-11）在窗口内。所以 H1 若成立，只可能是
> **客户端算的时间** 与 **我们报的时间** 不一致（客户端时钟/服务端时间戳/时区），而不是真的过期。
> M0 先花 5 分钟把这条排掉：登录时打一行服务端时间和客户端系统时间，再对照卡片。

- 三个都不中 → 不修卡片，**走 L3**（命令选关），把卡片记成“客户端资源限制”，不阻塞交付。
- 每次探针只改一个变量，报告写清“改了哪一行、看到几张卡、`challenge list: N entries / M groups`”。

### 4.4 结算与存档（M3，可与 M1 并行）

- 星数：按 `ChallengeTargetID` 算（`ROUNDS_LEFT` / `DEAD_AVATAR`，逻辑抄 Danheng `CalculateStars`），
  拿不到就退回固定 3 星。
- 历史：`saves/<uid>/challenge.json` → `{challenge_id: {stars, score, at}}`；
  `GetChallenge` 有历史用历史，没历史且 `unlock_all=true` 给满星。
- 结算时把历史写回，`ChallengeSettleNotify.max_level` 填真实最大值。

### 4.5 开关

```toml
[endgame]
mode = "emulator"      # emulator(A) | official(B)；B 保留现状，不删
moc_group_id = 0       # 0 = 按赛季时间自动选（2026-11-11 -> 1036 物竞天择）
unlock_all = true      # 所有层可选
```

## 7. 风险

1. **黑屏可能不是场景问题**：如果 M0 显示客户端根本不发第二次 `StartChallenge`，且两套阵容 + 换组后仍黑屏，
   下一批怀疑点是 `SceneBattleInfo` 里的 `battle_stage_id`（pearl 没填，存疑）与第二队 avatar 的 `LineupChallenge2` 标记。
   预案：把上半成功那局的 `SceneBattleInfo` 与下半逐字段 diff，按差异逐个试（每轮真机只改一个字段）。
2. **卡片可能不可修**：客户端资源决定的东西，服务端改不动。兜底是 L3 命令选关，已写进计划。
3. **`star=7` 是假数据**：玩家可见。M3 落历史后换成真实星数；在那之前报告里必须写明“满星是占位”。
4. **4.7.0 未覆盖**：`data/endgame.json` 是 4.6.54 导出的；4.7.0 客户端要另导一份（`export_endgame.py --resources` 已有参数）。
