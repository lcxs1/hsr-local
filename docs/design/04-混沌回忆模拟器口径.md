## 2. 现状（已核过的事实，不是猜测）

**数据层已够用**，缺的都在 UI 与两段式流程上：

- `data/endgame.json`：843 条（MOC 639 / PF 112 / AS 92），MOC 里 **629 条有 node2**（即上下半）。
- 混沌回忆是「一场景多楼层」：以当前赛季 group `1036`（物竞天择）为例，id `5501..5512` = 第 1..12 层，
  全部 `entrance=3013801 / plane=30138 / floor=30138001`，上半 `MazeGroupID1=4`、下半 `MazeGroupID2=5`。
  → **换层 = 换 challenge id**（同一场景），**换半 = 同场景内换实体组**。
- 已有实现：`hsr/game/services/endgame.py`（表）、`services/challenge.py`（状态/战斗包/`advance_stage`）、
  `handlers/challenge.py`（GetChallenge/StartChallenge/Settle/Leave）、`services/scene.py:452 build_challenge_scene`。
- 真机（`logs/test/test-20261111-181334.server.log`）：上半 id=15 打通；服务端 18:16:25 自动 `advance` →
  18:16:31 发下半 `SceneBattleInfo` → 18:16:47 客户端自己回 `WIN`，**画面是黑的**。

**两个具体缺陷（对得上参考实现）**：

1. `StartChallengeScRsp.lineup_list` 只回了**当前这一半**的一套阵容（`handlers/challenge.py:272`）。
   DanhengServer 与 LunarCore 在 `StageNum >= 2` 时**两套都回**。
2. 上半结束后是**重建整份 SceneInfo**再推给客户端（`services/challenge.py:277 advance_stage`）；
   参考实现是**原地卸载 group1、加载 group2**，再把当前这一套阵容切到 `LineupChallenge2`。

**卡片缺失的原因还没定死**（这是 §4.3 的探针任务）：

- 真机只出两张卡：`永屹之城遗秘 45/45`、`天瞳求仙迷航录 18/18`。
  45 = group `100`（15 层 × 3 星）、18 = group `900`（6 层 × 3 星）——即**我们发的 `star=7` 被按组汇总**了。
- 这两组在 `ChallengeMazeConfig` 里都**没有 `Floor` 字段**（常驻组）；带 `Floor` 的轮换组（1001–1037）一张卡都不出。
- 已知不是 `challenge_group_list` 驱动：发 109 个组仍只有 2 张卡（[03 §5](03-终局玩法.md)）。

**两个决定性的共同点**（三家完整实现都这么做，我们两家都没做）：

1. `StartChallengeScRsp` 在 `StageNum >= 2` 时 `lineup_list` **两套都发**

2. 下半是**同场景换组**，不是换场景。

不能等下半再想办法。

## 4. 设计

### 4.1 选关：三层，逐层兜底

- **L0 数据**：楼层清单来自 `data/endgame.json` 的某个 group；**选哪一组由时间决定**——用 `data/vendor/srtools-<日期>/endgame_index.json` 的 `BeginTime/EndTime` 取“当前赛季”，2026-11-11 是 `1036 物竞天择`（`5501..5512`），下一期才是 `1037 漆黑残响`；默认回落到最新期（12 层组）
  配置项 `[endgame] moc_group_id` 可换任意组（1001–1037 都是 10/12 层）。
- **L1 解锁**：12 层全部 `star=7` 下发（pearl 的写法，已验证客户端会显示为可打）；
  `GetChallenge` 里每层带 `taken_reward=42`。玩家想打第 12 层直接点。
- **L2 卡片**：补「物竞天择」（见 §4.3）。卡片没修好也不阻塞 L1/L3，只影响“看得见”。
- **L3 兜底（一定要做）**：聊天命令 `/moc <challenge_id>`（或 `/moc <floor>`）= pearl 的 custom mode。
  服务端记住 `session.pending_challenge_id`，下一次 `StartChallenge` 用它建战斗。
  这样即使卡片/楼层 UI 缺失，**任意关卡永远可打**，也是 A 口径的“逃生门”。

> 为什么不做「所有历史期都能选」：客户端楼层列表是它自己按**当前期**渲染的，
> 历史期不出现在 UI 里；服务端没法凭空造出旧期卡片。要跨期就用 L3 命令。

### 4.2 上下半：参考实现的“原地换组”（2026-11-11 深夜按参考实现重写，见 §5.4）

**StartChallenge（上半）**

1. 解析 `avatar_lineup_first` / `avatar_lineup_second`（`handlers/challenge.py:on_start_challenge`）。
2. 两套都进 `ChallengeState.phases`（`phases[0].team` / `phases[1].team`）。
3. 响应：`lineup_list=[Challenge 队, Challenge2 队]`（`challenge_service.lineups`），
   `cur_challenge.extra_lineup_type=LineupChallenge`；两条 `LineupInfo.index` 都是 0。
4. 场景 `build_challenge_scene(phases[0].node)`，并按这一队装配场上角色。

**上半 WIN → 下半（`challenge_service.advance`）**

`advance = "sync"`（默认）按 LunarCore `ChallengeInstance.advanceStage` 的顺序发：

1. `ChallengeLineupNotify(LineupChallenge2)` + `SyncLineupNotify(下半阵容)`（结果包**之前**）；
2. `PVEBattleResultScRsp`；
3. `SyncServerSceneChangeNotify`（告诉客户端“服务器场景变了”，它会整套重进）；
4. `EnterSceneByServerScNotify`：整份新 `SceneInfo`（角色组 = 下半队伍，`entity_group_list` 里声明
   `MazeGroupID2`）。

**不发任何 `SceneGroupRefreshScNotify`**：4.7.0 会拿“没声明过的组”去
`MapDef._ActiveServerHoyoGroup` 激活并 NRE（§5.4 第 10 行）。`advance = "inplace"`（旧的逐组 patch）、
`"scene"`（少了 `SyncServerSceneChangeNotify`）、`"client"`（pearl 流程，等服务端重发
`StartChallenge`）都只留作 A/B 探针。

**下半 WIN** → `ChallengeSettleNotify(FINISH, star)`；**LOSE** → `FAILED`；
`LeaveChallenge` 回进入前场景并关掉额外阵容。

**为什么不再重建场景**：客户端已经知道自己在哪个 arena 里，再塞一份新的 `SceneInfo`
（同 floor/entry、只换组）会让它的战斗区域初始化和场景对不上——现象正是“黑屏但战斗在跑
（16 s 后自己结算）”。4.6.54 与 4.7.0 都复现，是这条链最主要的根因候选。

**数据层还有一个坑（新数据才看出来）**：639 条 MOC 挑战里有 **130 条的上半是 2 个 stage**
（`EventList1` 两条，例如 `101` 上半 = 30001161「守护者之影」+ 30001162「蚕食者之影」），
我们和 pearl 现在都只取最后一条，等于**少打一场**。留给下一轮：一个半场多场战斗按顺序串起来
（同一场景换怪，不换队伍）。

### 4.4 结算与存档（M3，可与 M1 并行）

- 星数：按 `ChallengeTargetID` 算（`ROUNDS_LEFT` / `DEAD_AVATAR`，逻辑抄 Danheng `CalculateStars`），
  拿不到就退回固定 3 星。
- 历史：`saves/<uid>/challenge.json` → `{challenge_id: {stars, score, at}}`；
  `GetChallenge` 有历史用历史，没历史且 `unlock_all=true` 给满星。
- 结算时把历史写回，`ChallengeSettleNotify.max_level` 填真实最大值。

### 4.5 开关

```toml
[endgame]
moc_group_id = 0          # 0 = 按赛季时间自动选（2026-11-11 -> 1036 物竞天择）
unlock_all = true         # 所有层可选
advance = "sync"          # sync（默认，LunarCore 顺序）| declare / inplace / scene / client（A/B）
lobby_props = "crystals"  # 大厅报哪些组：all | crystals | none
lobby_entry = 0           # 0 = 用客户端请求的入口
lobby_grace_seconds = 0   # 传送场景推送压后（已证伪，别再靠它）
group_list = "all"        # M0 卡片探针：all | rewards
send_max_level = false    # M0 卡片探针：额外发 max_level_list
```

旧的 `advance = "refresh" / "none"` 仍然能读（分别映射到 `inplace` / `client`）。

### 5.3 4.7.0 真有「星启模式」：一层 3 个节点，协议是 Tierce

面板路线走通后（星际和平指南 → 忘却之庭 → 混沌回忆 → 物竞天择，12 层 / 36 星显示正常），

### 5.4 2026-11-11 深夜：混沌回忆逻辑重写（阶段状态机）

**为什么重写**：4.6.54 的 8 轮 + 4.7.0 的 5 轮真机里，「下半黑屏」「节点二战斗被拒」反复出现，
每次都在旧模型上打补丁（`advance=none|refresh|scene`、`tierce_nodes`/`tierce_teams` 与
`node`/`second`/`stage` 各存一份）。真正缺的是**一个阶段模型 + 一套和参考实现逐条对齐的包序**。

**新模型**（`hsr/game/services/challenge.py`）：一个挑战 = `phases: list[Phase]`，
每个 `Phase` = `(node, team, lineup_type)`；`index` 指向当前阶段。所有派生态
（`stage` / `second` / `stage_index` / `tierce_nodes` / `tierce_teams`）都是属性，
不再各存一份。

**这一轮改掉的 6 个具体偏差**（每条都对应一个真机症状）：

| # | 旧实现 | 参考实现 / 现在的写法 | 对上的症状 |
|---|---|---|---|
| 1 | 阶段切换先改状态再取阵容，`SyncLineupNotify` 发的是**下一队**的 `LineupInfo` | 只发 `ChallengeLineupNotify(new_type)`；跟参考一样不再手工塞额外阵容 | 下半战斗被客户端拒绝（4.7.0 收到 `SceneCastSkillScRsp` 后 16 ms 就 `QuitBattleCsReq`） |
| 2 | 额外阵容的 proto `index = type + 10`（11/13） | `index = 0` + `extra_lineup_type`（Danheng `LineupInfo.ToProto`：额外阵容 index 恒 0） | 同上（客户端按 index 找阵容） |
| 3 | `SceneGroupRefreshScNotify` 里塞 `state=0/1`，卸旧组+装新组混在一个包，还混角色组 | 每个组一条 `GroupRefreshInfo`，只填 `group_id/refresh_type=LOADED/refresh_entity`；卸、装、角色三件事分三包 | 4.6.54 `_RefreshGroup_Legacy` NRE（坑 35） |
| 4 | 退出挑战只清服务端状态 | `ChallengeLineupNotify(LineupNone)` + `SyncLineupNotify(普通阵容)` | 打完挑战后野外换队/开战错乱 |
| 5 | `CurChallenge.round_count` / `dead_avatar_num` 永远 0 | 用 `PVEBattleResultCsReq.stt.round_cnt` / `die_times` 累计 | 结算页永远「剩余轮 30」 |
| 6 | `GetCurBattleInfoScRsp` 没战斗时回空 body | 回一个**存在但为空**的 `SceneBattleInfo` | 登录时客户端 `_OnGetCurBattleInfoScRsp` NRE（`Player.log` 实证） |
| 7 | `SceneBattleInfo.rounds_limit` 恒 30 | 用配置的 `ChallengeCountDown` 与**剩余**轮次（跨半场共用，参考 `battle.RoundLimit = RoundsLeft`） | 结算页/HUD 轮次对不上 |
| 8 | `SceneCastSkill` 回显客户端给的目标实体 id | 只认当前场景里存在的实体，旧半场的 id 回落到当前怪 | 换半场后客户端拿旧 id 施放，回了已删实体 → 开不了战斗 |
| 9 | 换半场发「卸旧组」时用 `refresh_type=LOADED`（逐实体 delete） | **默认不卸载旧组**，只加载新组；真要卸载用 `refresh_type=UNLOAD`（`[endgame] unload_old_group`，未真机） | 4.7.0 真机 22:52/22:53/22:56：客户端报 `Reload ServerGroup Error, Already Exists!!! ServerGroupID: 9` → `MapDef._ActiveServerHoyoGroup` NRE → 黑屏「弱点」/卡在近战，**advance 之后一个 `SceneCastSkill` 都不发**（被迫重启） |
| 10 | 换半场用 `SceneGroupRefreshScNotify` **加一个没声明过的组**（`inplace`，不卸旧组） | 默认改成 `sync`：`ChallengeLineupNotify` + `SyncLineupNotify` → 结果包 → `SyncServerSceneChangeNotify` + `EnterSceneByServerScNotify`（整份新 `SceneInfo`，`entity_group_list` 里声明 node2 的组）；**不再发任何 `SceneGroupRefreshScNotify`** | 4.7.0 真机 23:07/23:10/23:13：`Already Exists` 没了，但每次 advance 仍有一条 `_OnSceneGroupRefreshScNotify` → `MapDef._ActiveServerHoyoGroup` NRE；实体已经进场景（下半 NPC 看得见）却攻击不动、零 `SceneCastSkill`，只能重启。客户端日志同一时刻自己重载了 stage（`AdventurePhase._EnterStep2` → `Map._LoadStage` 996256495），说明它本来就打算整套重进 |
| 11 | 换半场成功后：**下半战斗黑屏 ~15 s 后自己 WIN，直接到结算页**（玩家观感「战斗被跳过」） | 未定。`sync` 路线真机 23:25 / 23:27 两轮：进场景、按 F、`SceneCastSkillCsReq`、结果包、结算页全部按顺序发生；坏的是画面。新增 `battle stats:`（`round_cnt/total_auto_turns/cost_time/monster_list/伤害`）与 `challenge battle waves:` 两行日志，下一轮直接看客户端到底有没有真打 | `logs/test/test-20261111-232502.*`：`-47-advance+6.png` 正常画面，`-48-battle-info+4.png`/`-50/51/52` 全黑（~399 KB）；客户端零 NRE；`data/endgame.json` 的 `stages[30126012]` 与 pearl-sr `StageConfig.json` 的 `MonsterList` 完全一致（不是本地怪物数据缺失）。工作假设：客户端刚用 `SyncServerSceneChangeNotify` 重载完 stage（`Map._LoadStage` + `Unloading N unused Assets`），战斗在资源卸载竞态里启动 |

另外补了 `EnterChallengeNextPhaseCsReq` / `RestartChallengePhaseCsReq` 两条 handler：
前者**只重发当前阶段场景、绝不自己跳半场**（防止迟到请求吞掉半场），后者支持「重打本半场」。

**阶段切换的包序**（`advance = "sync"`，默认；参考 LunarCore `ChallengeInstance.advanceStage`）：

```text
ChallengeLineupNotify(Challenge2)    # 换阵容槽              ┐ 结果包之前
SyncLineupNotify(下半阵容)            # 同步阵容数据           ┘（客户端仍在战斗态，会处理）
PVEBattleResultScRsp                 # 结束这场战斗
SyncServerSceneChangeNotify          # 服务器场景变了 → 客户端整套重进
EnterSceneByServerScNotify(scene)    # 整份新 SceneInfo：角色组 + node2 迷宫组
```

为什么换成这条路：4.7.0 的客户端把 `SceneGroupRefreshScNotify` 里**它没在 `SceneInfo.entity_group_list`
里见过的组**当成 server group 去 `MapDef._ActiveServerHoyoGroup` 激活，直接 NRE；实体已经加进场景
（下半 NPC 看得见），但这个组没被注册成可攻击，于是按 F 只有近战动作、永远不发 `SceneCastSkillCsReq`。
真机还拍到同一个时间点客户端自己就重载了 stage（`AdventurePhase._EnterStep2` → `Map._LoadStage`），
说明它本来就等着「服务器换了场景」这个信号，只是我们以前没发。

**不要用 `refresh_type=LOADED` 去“卸载”组**：4.7.0 把它当成「激活这个组」，组已存在时报
`Reload ServerGroup Error, Already Exists` 并在 `MapDef._ActiveServerHoyoGroup` 里 NRE。
需要真卸载时用 `refresh_type=UNLOAD`（`[endgame] unload_old_group`），但 `sync` 路线压根不碰组刷新。

**A/B 探针**：`advance = "declare"`（原地声明组：`GroupRefreshInfo.group_info` = 整组
`SceneEntityGroupInfo`，不推场景、不触发客户端重载 stage）、`"inplace"`（逐实体 patch，4.7.0 必
NRE）、`"scene"`（只推新 `SceneInfo`、少了 `SyncServerSceneChangeNotify`）、`"client"`（等服务端
重发 `StartChallenge`，pearl 流程）。

**证据**：228 单测全绿 + `scripts/check.ps1` 全绿（`check_docs` 只剩 `AGENTS.md` 死链）；offline 回放
`challenge → 上半 → 换组 → 下半 → 结算 → 退出` 链（`hsr/replay.py:run_challenge_flow`）现在跑的就是
`sync` 路线，断言包序（`sync` 段不许出现 `SceneGroupRefreshScNotify`）、两队、只在下半结算、退出关阵容。
**未真机验证**：`sync` 路线还没跑过 4.7.0 真机（上一轮 23:07 的结论是 `inplace` 仍会 NRE）。

## 7. 风险

1. **下半黑屏可能不只是服务端问题**：本轮（2026-11-11 深夜）已把服务端能对齐的都对齐了
   （见 §5.4），但仍需一轮真机确认。若 `sync` 仍卡，下一批怀疑点：
   - `SyncServerSceneChangeNotify` 之后客户端到底重不重进（看 `AdventurePhase._EnterStep2` 之后
     有没有新的 `EnterSceneCsReq` / `GetCurSceneInfoCsReq`）；

   - `GroupRefreshInfo.group_info`（字段 5）声明整组这条路（如果 `sync` 的 `EnterSceneByServerScNotify`
     被客户端当成“同场景重进”而忽略，就回去补组声明）。
   每轮只改一个变量，报告写清改了哪一行、看到什么。
2. **卡片可能不可修**：客户端资源决定的东西，服务端改不动。兜底是 L3 命令选关。
