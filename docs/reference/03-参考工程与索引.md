|---|---:|---:|---:|

| echium（4.6.53/54） | 2621 | 2621 | 100% |

| Danheng 3.7.0 | 1724 | 8 | 0.5% |
| LunarCore 4.2.0 | 1188 | 19 | 1.6% |
| qingque | 1632 | 23 | 1.4% |

同一条命令在不同 build 的 id：

| 命令 | 4.6.54 | pearl | Danheng 3.7 | LunarCore 4.2 | Himeko 4.5 |
|---|---:|---:|---:|---:|---:|
| `PlayerGetTokenCsReq` | 5 | 5 | 83 | 14 | 44 |
| `GetBasicInfoScRsp` | 20 | 20 | 4 | 36 | 9 |
| `GetGachaInfoCsReq` | 1974 | 1974 | 1999 | 1991 | 1932 |
| `StartCocoonStageCsReq` | 1444 | 1444 | 1474 | 1425 | 1494 |

**做法**：

1. 参考工程里按**名字**找 handler；
2. 在 `hsr-local/proto/CmdId.json` 查 4.6.54 的 req/rsp id；
3. 把字段号/消息名在 `proto/StarRail.proto` 里对一遍；
4. 落地到 `hsr/game/handlers/<域>.py` + `hsr/game/services/<域>.py`，写成
   `router.add("XxxCsReq", fn)`。

坑：`QuickStartFarmElementCsReq` 在 pearl 里叫这个名字，4.6.54 表里叫
`StartQuickFarmElementCsReq`；`GetMatchPlayDataRsp` 不是 `...ScRsp`
（`rsp_name_of()` 已加 `Rsp` 回退）。

## 3. “4.7 快照”的真相

`pearl-sr` 自称“4.7 beta”，但协议快照就是 4.6.54 的导出：

1. `README.md` 写 4.7 beta，但它给的客户端下载是 4.5.5X / 4.6.5X；
2. `hotfix.json` 最高只到 `OSBETAWin4.6.54`；
3. `git log -1` = `2026-10-23 Update 4.6.54 CN hotfix`；
4. `protocol.pb.zig` 有 **5051** 个消息，和 4.6.54 的 `StarRail.proto` 描述符一致；
5. 两份命令表 **2586 个同名命令 id 完全一致**。

所以 `tools/out/4.6.54-vs-4.7-beta-*` 里的“0 改号”是**同一份表和自己比**；
“36 个重命名”多半是社区命名规范化（`LockEquipmentCsReq → CmdLockEquipmentCsReq`）。

真 4.7 到手时：

- 第一件事是重新提 CmdId 表，不拿 pearl 当基线；
- `tools/cmd_diff.py` 要加 `--align name`；
- `tools/proto_diff.py` 的 `pair_renames()` 要覆盖 common 消息。

正面价值：现在有 `Himeko 4.5`（4651 消息）和 `pearl 4.6.54`（5051 消息）两个
真实不同 build 的快照，可做真跨版本回归。

### 3.1 真跨版本 diff 演练（已生成产物）

```powershell
cd E:\LCXS
pwsh tools/snapshot.ps1 -Name 4.5 `
  -ZigRoot reference-projects/Himeko-Nova-SR/protocol/src/root.zig `
  -ZigPb   reference-projects/Himeko-Nova-SR/protocol/src/protocol.pb.zig
# -> tools/out/4.5/{CmdId.json,schema.json}：2539 命令 / 4651 消息 / 601 枚举

pwsh tools/diff.ps1 -Old tools/out/4.6.54 -New tools/out/4.5 -Title "4.6.54-vs-4.5-himeko"
# -> tools/out/4.6.54-vs-4.5-himeko-{cmd,schema}.md
```

结果暴露两个工具的口径问题：

| 报告 | 输出 | 问题 |
|---|---|---|
| `cmd_diff` | `renamed_ids 1070` / `new_ids 1459` / `gone_ids 1540` / `moved_names 2002` | 按 id 对齐在真跨版本完全失真（满屏“id reused?”） |
| `proto_diff` | `common_messages 2761` / `breaking_messages 2296` | 先按消息名配对；4.6.54 混淆名对不上，真正靠字段签名配上的只有 132 个 |

结论：两个 diff 工具是为“同源快照 + 社区改名”设计的，**不能直接用于真 4.7 的破坏性判定**。

## 6. 可借鉴的工程做法

| 参考 | 做法 | 对 hsr-local 的意义 |
|---|---|---|
| Danheng | 一个命令一个 Handler 类 + 一个响应一个 Packet 类 | 命令数上到 100+ 后，可只在复杂命令（挑战/抽卡）引入 `services/<域>/packets.py` |
| Danheng | `ServerSideProto/`：用 protobuf 定义服务端存档结构 | 挑战/模拟宇宙这类深层状态比手写 dict 安全 |
| Danheng | Muip HTTP 管理 API（RSA + session） | 本项目 FastAPI 已跑 21000，加 `/admin/*` 成本低，但只监听 127.0.0.1 |
| Danheng | 游戏内命令系统 + `GameConstants` 集中 magic id | 本项目只有 Lua 控制台；做挑战/抽卡时可加最小 `!give/!stage/!tp` |
| LunarCore | 23 个命令类 + `@ResourceType` + 反射 loader | 可写 Python 版 `dataclass + @resource("CocoonConfig.json")` |
| pearl/Himeko | `services/` + `manager/` + `data/` + `utils/logic.zig` | 与本项目 `handlers/services` 同构，纯函数部分可直接翻译 |
| Himeko | `lua.zig`：目录读脚本 + 单调递增 version | 比本项目的 `exec=tt/tf` 标记更省心，可借鉴 |
| qingque | `config/lx/lx.go`：Lua 持久化 + mtime 重载 + SRTools | 接 SRTools 时可抄格式 |
| echium | `sdkserver/__main__.py::fetch_from_official` | 从官服拉 hotfix 并缓存；升级时的 CDN 来源 |

### 6.1 把 pearl/Himeko 当“活参考”

`run/pearl-sr/launcher/` 和 `reference-projects/Himeko-Nova-SR/launcher/` 里是同一套客户端补丁
（`launcher.exe` + `hkrpg.dll`），`baseline/4.6.54/` 里也有一份。

- pearl（TCP + 补丁）用本地 4.6.54 客户端大概率能跑；
- Himeko 要 4.5.5X 客户端，本机没有，只能读代码；
- 遇到“这个 UI 面板到底回什么字段/Notify 顺序”时，先用 pearl 跑一遍 +
  `tools/collect.ps1` 抓流量，得到“标准答案抓包”；
- pearl 和 hsr-local 不能同时挂在同一个客户端上，切回去前还原
  `hkrpg.dll`/`launcher.exe`，或从 `baseline/4.6.54` 起干净客户端。

## 7. 传输层交叉校验

hsr-local 的握手/帧/KCP 已 4.6.54 真机验证，但 Danheng 有 3 处差异，
是“新客户端不认旧服务端”的排查清单：

| 项 | hsr-local 现状 | Danheng 实现 | 建议 |
|---|---|---|---|
| 握手码 | 只认 `0x000000FF`(255) / `0x00000194`(404)，且 `looks_like_request()` 只匹配 `00 00 00 ff`、`00 00 01 94` | 还认 `-934149376` = **`0xC8520300`**（`DanhengListener.cs:101`） | 4.7 抓包时若“有 UDP 包但服务端不认”，先加白名单 |
| 握手响应第 3 字段 | 固定 `00 00 00 00` | 回显客户端第 12 字节的 `enet` | 4.6.54 不校验；升级兜底可加（一行） |
| 断连 | 收到 404 直接关会话，不回包 | 回 20 字节 `0x194 · conv · code · 0x19419494` | 客户端退出偶发卡 5 秒时可试回 ack |
| 会话 8 字节 | `conv(u32 BE) + token(u32 BE)`，KCP 里 `LE(conv)+LE(token)`（tap 验证） | `BinaryWriter` 写 high32/low32，conv 是小整数计数器 | 保持现状；`kcp_conv_mode` 双模式是正确设计 |
| KCP 参数 | `nodelay(1,10,2,1)`、窗口 256、MTU 1400、overhead 28 | KcpSharp：MTU 1400、窗口 256/256、`UpdateInterval=100`、keepalive 1s/30s | 参数同族；新客户端丢包/卡 3 秒先试 `UpdateInterval`/keepalive |
| 包加密 | 无 | `Crypto.cs`：`Ec2b` 密钥 + MT19937 生成 4096B XOR key，逐包 XOR | 4.6.54 不需要；新 build 若加密，这是唯一现成实现 |
| 帧日志 | `packets.log` DEBUG | `PacketLogHelper.ConvertPacketToJson`：opcode+payload 解成 JSON | 可给 `decode.py` 加“按会话落 JSON 帧日志” |

## 8. 移植配方

```python
# hsr/game/handlers/lineup.py（示例：GetLineupAvatarDataCsReq）
async def on_lineup_avatar_data(session: Session, req: pb.GetLineupAvatarDataCsReq):
    data = [
        pb.LineupAvatarData(id=avatar_id, hp=..., avatar_type=pb.AVATAR_TYPE_FORMAL)
        for avatar_id in session.lineup.slots          # 用当前形态 id
    ]
    return pb.GetLineupAvatarDataScRsp(avatar_data_list=data)

def register(router: Router) -> None:
    router.add("GetLineupAvatarDataCsReq", on_lineup_avatar_data)
```

步骤：

1. **查名**：参考工程里定位 handler（Danheng `Recv/<域>/Handler*.cs`、
   pearl `services/*.zig` 的 `handlers.zig`、LunarCore `packet/recv/*.java`）。
2. **对 id**：`Registry.id_of("XxxCsReq")` 拿 4.6.54 的 id；**不要**抄参考里的常量。
3. **对字段**：在 `proto/StarRail.proto` 核对字段号；社区名（`pos_index`/`entry_id2`）
   按字段号找。
4. **落地**：`handlers/<域>.py` 只做“读请求 + 调 service + 回响应 + 按需 notify”；
   数据逻辑放 `services/<域>.py`；新增数据放 `data/<域>.json`，并在
   `hsr/config_check.py` 加交叉校验（`--strict` 会跑）。
5. **测**：`tests/test_<域>.py` + `hsr/replay.py` 加离线链路；
   `scripts/check.ps1` 会跑单测 + 5 链路回放 + proto + ruff + docs。
6. **验**：`tools/capture_report.py --handlers run/hsr-local/hsr/game/handlers`
   看该命令从 `dummy` 变成 `handled`；真机再跑 `scripts/game_test.ps1`。
