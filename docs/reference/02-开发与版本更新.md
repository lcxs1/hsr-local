## 0. 一页结论

1. **私服是「状态提供者」，不是游戏模拟器**：80% 的工作量是构造合法 protobuf。
2. **包体不是猜出来的**：protobuf schema、cmd id、资源 id 都来自客户端或其导出产物；
   靠抓包 + 试错补的是**字段语义和取值**。
3. **请求→响应靠「表 + 命名约定」**：`XxxCsReq → XxxScRsp`，但两个 cmd id 是独立随机数，
   每个版本可能增删，必须抄表并验证。
4. **客户端对空响应/未知命令极其宽容**：这是“30 个 handler 就能进游戏”的原因。
5. **客户端逆向分三层**：数据层（proto/cmd/资源表）**必需**；局部控制流按需；全量不必要。
6. **版本更新**：build 变了必须重新核对 hotfix、CmdId、proto、资源表、抓包样本；
   handler 逻辑、存档格式、工具链通常不用重写。
7. **数据获取优先级**：社区导出 → 现成私服/发行包 → 客户端静态提取 → 运行时导出 → 抓包验证。
   不要一上来反编译 563MB 的 `GameAssembly.dll`。

### 0.1 速答

| 问题 | 答案 |
|---|---|
| 作者怎么做出私服？ | 抄客户端数据 + 参考/反编译实现 + 抓包 + 最小闭环试错 |
| 怎么知道包体对应哪个返回？ | 客户端 schema + cmd 表 + `CsReq→ScRsp` 约定 + 真实流量验证 |
| 有必要逆客户端控制流吗？ | 数据层必需；局部按需；全量不必要 |
| 客户端更新要重提数据吗？ | 要，但只重提“数据”，不重写“代码” |
| 数据具体怎么拿？ | 社区导出 / 现成私服 / IL2CPP / 抓包 / 运行时内省 |

## 2. 通信栈

```text
StarRail.exe
   ├─(1) HTTPS query_dispatch / SDK JSON ──代理劫持──> 127.0.0.1:21000
   ├─(2) HTTPS query_gateway (base64 protobuf) ────────┘
   └─(3) UDP 23301  20B 握手 → KCP → 帧(cmd + protobuf)
```

- 前两步由代理把登录域名改写到本机；服务端不处理 TLS；
- 第三步裸 UDP，不加密；
- 必须实现 `query_dispatch` / `query_gateway` / `exchange` / hotfix。
- 本项目 KCP 已判定为 `u32_le_token`（28B 头，LE(conv32)+LE(token32)）。

完整接口、字段和命名坑见 [../design/01-网络与登录](../design/01-网络与登录.md)。

## 3. 包体知识从哪来

### 3.1 schema：来自客户端

`proto/StarRail.proto` + `CmdId.json` 来自与 4.6.54 同源的导出；本项目用
`proto/hsr.desc` 做动态解码。**不要手写消息定义**，字段号是权威。

### 3.2 cmd id：不能猜，必须抄表

```python
# 请求名和响应名只有一条规律：结尾 CsReq 换成 ScRsp。
# GetAvatarDataCsReq(374) → GetAvatarDataScRsp(319)
# 两个号是各自独立的随机值，不能靠加减推算。
```

每个 build 都会整体重排：4.6.54 的 `PlayerGetTokenCsReq` 是 5，
Danheng 3.7 是 83、LunarCore 4.2 是 14、Himeko 4.5 是 44。

### 3.3 请求→响应：命名 + 表兜底

`XxxCsReq → XxxScRsp` 是主规则；但也有 `GetMatchPlayDataRsp`（1027）这种不是
`...ScRsp` 的特例。`registry.rsp_name_of()` 先找 `ScRsp`，再回退 `Rsp`。

### 3.4 字段值：抓包、资源表、试错

| 来源 | 例子 | 位置 |
|---|---|---|
| 真实/参考流量样本 | `PlayerLoginScRsp.basic_info` 字段号 1/2/4/8；`plane_id=20313` | [01-登录序列与基线](01-登录序列与基线.md) |
| 资源表 | 关卡波次、场景实体、挑战 buff | `pearl-sr/resources` |
| 行为反馈试错 | 缺字段会闪退/软锁；`battle_id` 必须递增 | [../design/02-玩法与数据](../design/02-玩法与数据.md) |

### 3.5 客户端容忍度

首登 100 帧 69 条请求里只处理 19 条也能进游戏。安全默认值：
**未知命令回空 `ScRsp`，无对应响应就静默，绝不崩**。

## 4. 字段语义：凝滞虚影

```text
StartCocoonStageCsReq { cocoon_id, wave, prop_entity_id }
  → StartCocoonStageScRsp {
      prop_entity_id, cocoon_id, wave,
      battle_info {
        battle_id, world_level, stage_id, rounds_limit, logic_random_seed,
        monster_wave_list[], battle_avatar_list[], buff_list[]
      }
    }
PVEBattleResultCsReq → PVEBattleResultScRsp {
  end_status = req.end_status, battle_id = req.battle_id, stage_id = req.stage_id
}
```

必填字段缺了会闪退/软锁：`battle_avatar_list` 不能空、`stage_id` 必须存在、
`monster_wave_list` 不能空、`battle_id` 每场递增。常见失败模式见
[../design/02-玩法与数据](../design/02-玩法与数据.md) §7.7。

## 5. 客户端逆向：需不需要控制流

| 层 | 是否必需 | 手段 |
|---|---|---|
| 数据层（proto/cmd/资源表） | **必需** | 导出表、`hsr.desc`、资源 JSON |
| 局部控制流（网络/分发/消费） | 按需 | 抓包、Lua 探针、Player.log |
| 全量控制流（战斗/UI/渲染） | 不必要 | 客户端自己算 |

优先用替代手段：

| 目的 | 手段 |
|---|---|
| 实际发了什么/回了什么/顺序 | UDP tap + 离线解码（`E:\LCXS\tools`） |
| 客户端内部状态/UI 行为 | Lua 注入（走心跳，不需要 IL2CPP） |
| 字段语义/取值 | 抓包对照 + 改一个字段看反应 + `Player.log` |
| 闪退/软锁 | 最后 N 帧日志 + 二分注释 handler |

本机客户端：`GameAssembly.dll` 563MB、`global-metadata.dat` 106MB（`MHY\0` 头，
非标准 `0xFAB11BAF`）、DesignData 275MB、Lua 52MB、AssetBundle 66GB。
`global-metadata.dat` 需要先解密/脱壳，是客户端分析的第一道坎；本项目目前**没有**
做 metadata dump（见 [../design/01-网络与登录](../design/01-网络与登录.md) §4）。

## 6. 版本更新：什么必须重做

### 6.1 三种更新

| 类型 | 例子 | 影响 |
|---|---|---|
| 小版本 build | 4.6.53 → 4.6.54 | 局部变化，逐项核对 |
| 大版本 | 4.6 → 4.7 | cmd id 全重排、资源表重导、部分消息改字段 |
| 纯 hotfix | 同 build 的 CDN 变化 | 只改 `hotfix.json` |

### 6.2 必须重新提取/核对的 5 类数据

1. **CmdId**：按命令名对齐，不能按 id；
2. **proto/schema**：消息字段增删、改名、类型变化；
3. **hotfix**：新 build 的 CDN 地址；
4. **资源表**：角色、关卡、怪物、挑战、教程、活动；
5. **抓包样本**：首登序列 + 关键玩法动作。

### 6.3 通常不用重写

服务端状态机、handler 业务逻辑、存档格式、工具链。
但**要复查**：字段别名、`versions/<build>.toml`、资源表字段名。

### 6.4 cmd 表会不会重排？

会。跨版本同名命令保持同 id 的比例只有约 0.5%~1.6%（见
[../design/01-网络与登录](../design/01-网络与登录.md) §5）。
“4.7 beta”的 pearl 快照其实是 4.6.54 导出，不能当 4.7 结论。

> **2026-11-11 实测更正**：同一版本线的 **beta 4.6.54 → release 4.7.0** 之间，cmd id **没有重排**，
> 4.6.54 的 `CmdId.json` 能完整解出 4.7.0 的首登 333 帧；实测细节与接入清单见
> [05-4.7.0兼容性实测](05-4.7.0兼容性实测.md)。跨大版本（如 4.6→4.7.0 的下一版、或 4.5→4.6.54）
> 仍然必须按名字重新对表。

### 6.5 症状 → 原因

| 症状 | 先查 |
|---|---|
| 登录卡在连游戏服前 | `query_gateway` / `exchange` 404、hotfix 缺失 |
| 游戏服连上但无后续帧 | KCP 头编码、握手响应、`conv` 布局 |
| 某功能空列表/无反应 | cmd 改号、响应消息改名、handler 未注册 |
| 字段错位/闪退 | proto 字段号变化、混淆名 |
| 资源加载失败 | hotfix CDN、资源表 id 不匹配 |

### 7.2 proto

从客户端/同源导出拿 `.proto`，`protoc` 生成 pb2 + desc；不要运行时从客户端动态生成。
换 build 时重新生成并跑 `scripts/check_proto.py`。

### 7.3 CmdId

从客户端枚举/`dump.cs`/描述符提取；与旧表做 diff 时**按名字对齐**。
`tools/cmd_diff.py` 目前默认按 id；真跨版本要加 `--align name`。

### 7.4 资源表

- 短期复用 `pearl-sr/resources`（与 4.6.54 同源）；
- 长期要自己从客户端 `DesignData/*.bytes` 解析（格式未破，需要专门管线）；
- 本项目只导出需要的子集：`stages` / `tutorials` / `progress` / `endgame`。

### 7.5 hotfix

按 `OSBETAWin*` key 查表；未知版本回退到最接近的已缓存版本。
官方地址可以从现有客户端/官方网关拉一次再写回；需要联网时按 [AGENTS.md §6](../../AGENTS.md) 的
受限例外执行（默认关闭、缺 key 触发一次、成功落盘、失败回退本地表）。

### 7.6 freesr-data

角色/光锥/遗器由 SR Tools 生态维护；服务端只读 + 热更新。
`battle_config` 目前只落盘，不参与战斗。

### 7.7 抓包

`E:\LCXS\tools\tap.py`：UDP 透明中继 + KCP 解码；`collect.ps1` 一键 tap + 服务端 + 汇总；
`capture_report.py` / `capture_diff.py` 做分类/对比；`freeze_baseline.py` 冻结基线。

## 9. 4.7.0 升级清单（方法论）

> 2026-11-11 已做首轮实测并落地：包体到手、协议兼容性已判定，`versions/4.7.0.toml` 与本地 CDN 回放
> 已实现，结论/落地记录见 [05-4.7.0兼容性实测](05-4.7.0兼容性实测.md) §5。本节保留为方法论清单。

### 9.1 核心判断

- 4.6.54 是现在唯一能产真实流量的版本；更新后可能被 `hdiff.exe` 覆盖；
- 顺序：**先冻结 → 跑通工具链 → 做 diff 基线 → 一键脚本**；
- `pearl-sr` 的“4.7 beta”是 4.6.54 同源快照，不能当 4.7 基线；
- 实到手的 4.7.0 CN 客户端：**cmd 表可直接复用 4.6.54 的**（实测），主要工作是 hotfix/资源校验路径
  与个别空回包导致的客户端 NRE，见 [05](05-4.7.0兼容性实测.md)。新版本缺 hotfix 条目时，
  可开 `features.hotfix_auto` 让服务端向官方网关取一次并落盘（[AGENTS.md §6](../../AGENTS.md) 的限制仍适用）。

## 12. 风险与注意事项

1. **本文没有完整演练过真升级**：等真实新客户端/协议文件，不要造假 profile。
2. **不要把 4.7/4.5 的资源表混进 4.6.54**：id 撞车会让客户端软锁。
3. **不要把社区规范化名当真实字段名**：字段号才是权威。
4. **不要指望直接跑参考工程联调**：端口/证书/客户端版本/传输方式都不同。
5. **管理接口只监听 127.0.0.1**：本地单人也不要把 Muip/命令接口暴露到公网。
