## 2. 观察

1. **登录完成（#90）之前就把场景发了（#88）**：客户端不等 `PlayerLoginFinish` 才进场景。
2. **大量活动/肉鸽/社交请求**在首登就发出来，绝大多数可以静默。
3. **`GetMissionStatusCsReq` 连发 8 次**，body 从 5 字节到 1.5KB，每次都要回。
4. **`GetMainMissionCustomValueCsReq` 完全没响应也能过**（silent）。
5. **`GetSecretKeyInfoCsReq`（cmd 30）是空响应**，后续包**没有加密**。
6. **`SceneEntityMoveCsReq`（1474）** 占全量 C→S 的绝大多数；可以忽略，
   要回就把 `entity_motion_list` 原样带回。
7. **心跳从 #253 才明显出现**；首登阶段客户端在忙着拉数据，心跳间隔约 5s。
8. **登出后重登**（#410 之后）会重新走完整首登序列；服务端要支持第二次握手/新会话。
9. **未知 cmd 8541** 发了但无影响 —— 未知命令静默是安全策略。
10. 服务端响应体可以是 0 字节（`GetCurAssistScRsp`、`GetMissionDataScRsp` 等）。

## 4. 黄金基线（2026-11-09）

| 指标 | 值 |
|---|---|
| 帧数 | 499（C→S 259 / S→C 240） |
| 唯一命令 | 317（其中 C→S 请求 166 个） |
| UDP 数据报 | 1,025 |
| KCP 布局投票 | `hsr28` × 1025，`kcp24` × 0，无 fallback |
| 未解析消息 | 0 |
| 握手 | 2 帧（1 C + 1 S） |
| 帧魔数偏移 | 全部 0（布局没变） |

本次只做到「登录 → 进场景 → 走动 → 打开若干界面」，没有打怪/结算，所以帧数比
§1 的 752 帧少；但**前 69 条 C→S 请求与 §1 逐条完全一致**。

握手请求实际是：

```text
000000ff 000000ff 00000000 00000000 ffffffff
```

即保留字段（第 4–11 字节）**不是全 0**，服务端/抓包工具不能要求它是 0。

按 `unknown_mode=empty_rsp` 分类（冻结当天）：

| 类别 | 唯一请求数 | 含义 |
|---|---:|---|
| handled | 34 | 有 `router.add(...)` |
| dummy | 116 | 无 handler，但存在对应响应消息 → 回空 body |
| silent | 2 | 无 handler、也无响应消息 → 不回包 |
| unknown | 1 | CmdId 表里没有这个 id |

后来补了 1498/589/752 三个纯回执后，按当前代码应为 **handled 36 / dummy 114**；
上表保留冻结当天的数字。

## 5. 怎么用它做升级对照

> 以下命令在 `E:\LCXS` 下执行（工具链不在项目内）。

```powershell
cd E:\LCXS

# 冻结（已生成，重抓后覆盖）
python tools/freeze_baseline.py --capture tools/captures/<dir> --name 4.6.54 `
  --cmdid tools/out/4.6.54/CmdId.json --handlers run/hsr-local/hsr/game/handlers

# 新版本到手后对比
python tools/capture_diff.py --old tools/golden/4.6.54/capture.bin `
  --new tools/captures/<new>/capture.bin `
  --old-cmdid tools/out/4.6.54/CmdId.json --new-cmdid tools/out/4.7.5X/CmdId.json `
  --md tools/out/capture-4.6.54-vs-new.md

# 单份抓包分类
python tools/capture_report.py --capture tools/golden/4.6.54/capture.bin `
  --cmdid tools/out/4.6.54/CmdId.json --handlers run/hsr-local/hsr/game/handlers
```

`tools/golden/4.6.54/` 里：`capture.bin`（原始帧）、`sequence.json`
（`(dir, cmd, len, sha1)` 扁平列表，对比首选）、`report.md`/`report.json`
（完整分类）、`summary.json`（计数/Top 命令/风险命令）、`README.md`（基线来源）。

下次抓包建议补的动作：

1. 打一场怪（`PVEBattleResultCsReq/ScRsp`、`SceneBattleInfo`）；
2. 开一次跃迁/传送（`EnterSceneCsReq` 字段 9 是 `teleport_id`，4.6.54 混淆名 `entry_id2`）；
3. 切一次队伍（`SyncLineupNotify`）；
4. 领一次任务奖励（`GetMissionStatus` 之外的任务结算链）。

## 6. 版本口径提醒

- `run/pearl-sr` 自称 "4.7 beta"，但它的协议快照**就是 4.6.54 的导出**：
  hotfix 只到 `OSBETAWin4.6.54`、`protocol.pb.zig` 恰好 5,051 个消息、
  2,586 个同名命令 100% 同号。所以 `tools/out/4.6.54-vs-4.7-beta-*` 里的
  “0 改号 / 0 破坏性变更”是**同一份表和自己比**。
- 真正可用的跨版本对照是 `reference-projects/Himeko-Nova-SR`（4.5，4,651 消息 / 2,539 命令）：
  同名命令只有 10/2,012 保持同 id，说明 **cmd id 随 build 重新分配**。
- 跨版本对齐要按“命令名 + 消息字段签名”，不要按 id；详见
  [03-参考工程与索引](03-参考工程与索引.md) 与 [02-开发与版本更新](02-开发与版本更新.md)。
