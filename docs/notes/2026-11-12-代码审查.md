## 1. 高危（1 项，建议优先修）

### 1.1 客户端可控的 slot 无上界 → OOM / DoS

- **位置**：`hsr/game/services/lineup.py:32-35`（`LineupState.set_slot`）
- **触发链**：`hsr/game/handlers/lineup.py:48`（`on_replace` 的 `slot_data.slot`）、`:60`（`on_join` 的 `req.slot`）都把客户端包的 `slot` 直接传给 `set_slot`。
- **问题**：

  ```python
  def set_slot(self, slot: int, avatar_id: int) -> None:
      while len(self.slots) <= slot:   # slot 无上界
          self.slots.append(0)
      self.slots[slot] = avatar_id
  ```

  只要带一个**合法** avatar id（如 1001），再发 `slot = 2**31-1`（或任意大值），`while` 就会 append 数十亿个 0，耗尽内存（MemoryError / OS OOM killer）。异常虽会被 router 吞掉，但列表已被撑到巨大、session 状态被破坏。这是对不可信输入的未受限分配，是本次审查中最明确的 DoS。
- **附带缺陷**：`set_slot(-1, base)` 会走 `self.slots[-1] = base` 静默覆盖最后一名队友（负索引未被拒绝）。
- **建议**：在 `set_slot`（或 handler 入口）钳制 `0 <= slot < team_size`（`team_size` 见 `world.team_size`，默认 4），`leader` 同样钳制；负值直接拒绝。

## 2. 中危

### 2.1 回包发送在 try 之外 → 单次编码失败永久杀死会话 worker

- **位置**：`hsr/game/router.py:90`（对比 80-87 行的 try 范围）
- **问题**：`dispatch` 的 `try/except` 只包住 `await fn(session, req)`，而 `await session.send(rsp)`（90 行）在保护之外。`session.send → registry.encode` 可能抛 `ProtocolError`（响应名不在 CmdId.json）或序列化错误；该异常逃出 `dispatch` 后命中 `session.py:218` 的 `except Exception`（它在 `while` 循环**外**），打印 “session worker crashed” 后 `_run` 直接结束——此后该会话所有后续包进不了处理器，直到 queue 满（1024）被丢弃，会话半死不活且不关闭。
- **建议**：把 `await session.send(rsp)` 也纳入 try；或让 `session._run` 在单包异常后 `continue` 而不是退出循环。

### 2.2 客户端可控的重复字段数量 → 响应放大

- **位置**：`hsr/game/handlers/scene.py:38-41`（`on_scene_map_info`）
- **问题**：`count = max(1, len(req.scene_identifiers))` 后 `[build_map_info(session) for _ in range(count)]`。`scene_identifiers` 数量只受 8 MB 帧上限约束，畸形包可塞数百万个 identifier，逼服务器构建数百万份 `SceneMapInfo`（每份含 `maze_group_list` 等子列表），造成内存/CPU 放大（OOM 场景）。
- **建议**：给 `count` 设合理上限（已知楼层数或小常数）。

### 2.3 本地 HTTP 服务无鉴权 + CORS `*`

- **位置**：`hsr/dispatch/app.py` 的 `/srtools`（POST）、`/srtools/export`（GET）、`/admin/freesr/reload`（POST）、`/debug/challenge`、`/debug/crystal`；CORS 头 `app.py:43-48` 为 `Access-Control-Allow-Origin: *`。
- **问题**：这些端点全部无鉴权，靠“只绑 127.0.0.1”兜底（默认安全）。但 ① `Access-Control-Allow-Origin: *` 意味着**任何**浏览器里打开的网页都能向 `http://127.0.0.1:21000/srtools` 发跨域 POST/GET，读写/清空角色数据（CSRF 式本地服务攻击）；② 一旦有人把 `[server].listen` 改成 `0.0.0.0` 或局域网 IP，这些端点连同 UDP 游戏口、`/cdn` 一起全网暴露且无认证。
- **影响**：当前只影响本地角色数据（无真实机密），但属于真实暴露面。
- **建议**：CORS `Allow-Origin` 收紧到 SR Tools 的真实 origin（或保留 `*` 但明确仅限回环）；对 `/admin/*`、`/debug/*`、`/srtools` 增加简单的 loopback 校验或 token；启动时对 `listen != 127.0.0.1` 打显式警告。

### 2.4 剩余轮次为 0 时被重置为满轮次

- **位置**：`hsr/game/services/challenge.py:1000-1005`（`battle_info`）
- **问题**：`rounds_limit=max(1, remaining) if remaining else rounds_limit(state.mode)`。当 `state.rounds_left` 恰好减到 0（玩家用完全部 30/4 轮）时，三元走 `else` 分支，把 `rounds_limit` 重置为 `DEFAULT_ROUNDS`(30)/PF(4)，等于又给满轮次。轮次预算语义是“跨半场共用”（998-999 行注释自己写明），0 应保持 0（或 `max(1,...)`），不该重置。
- **建议**：`rounds_limit=max(0, remaining) if state.rounds_left is not None else rounds_limit(state.mode)`，并对 0 显式处理（拒开战或给 1）。

### 2.5 存档 flush：时间戳先于写成功推进 + 无 fsync

- **位置**：`hsr/game/services/save.py:91-105`（`flush`）
- **问题**：① `self._last_write = now`（95 行）在 `try` 之前；若 `write_text`/`replace` 抛 OSError（磁盘满/权限），异常被捕获只记日志，但 `_last_write` 已被推进，后续 5 秒内的 `flush()` 全被节流跳过，内存里的最新状态静默不落盘。② tmp+replace 保证了原子替换（不会写坏档，这点正确），但 `write_text` 后无 `fsync`，断电仍可能丢尾部数据。
- **建议**：把 `_last_write = now` 移到写成功之后；必要时对 tmp 文件 `fsync` 后再 `replace`。

### 2.6 阵亡数跨重试累积、不随重打回退

- **位置**：`hsr/game/services/challenge.py:940-942`（`apply_result_stats`）+ `hsr/game/handlers/challenge.py:509-525`（重打本半场）
- **问题**：`dead_avatars` 只增不减；`RestartChallengePhase` 重打本半场时只回退 `rounds_left` 到 `phase_start_rounds`，却不清 `dead_avatars`。同一角色重打多死几次，`CurChallenge.dead_avatar_num` 虚高（当前星级硬编码 3/0，此字段只影响 HUD 显示，故列中不列高）。
- **建议**：给 `ChallengeState` 加 `phase_start_dead_avatars`，重打时与轮次一起回退。

### 2.7 回放「完整队伍」断言被截断 → 覆盖缺失

- **位置**：`hsr/replay.py:334`、`:369`
- **问题**：`[base_id(a) for a in first][: len(battle_avatar_list)]` 用战斗队员数截断期望队伍，前缀匹配即通过——当战斗队员少于完整队伍时断言形同虚设，回放并未真正覆盖“完整队伍”链路。
- **建议**：断言队伍长度与内容完全相等，而非前缀。

## 4. 已确认无问题（正面结论，避免误报）

- **危险调用 0 命中**：全仓库无 `eval/exec/pickle/subprocess/shell=True/yaml.load/os.system/unlink/rmtree`。
- **路径安全**：`local_cdn.lookup` 只取 basename 查固定索引，不拼接客户端路径，天然挡目录穿越；只服务 `client_dir` 下两个根。
- **官方网关请求**：`official.py` 参数走 `QUERY_KEYS` 白名单（丢弃 account/token 类），host 硬编码、5s 超时不重试，`asyncio.to_thread` 离环执行。
- **帧解析**：`frame.py:parse` 先做 `len(buf) != expected` 再校验 MAX，不信任不可信长度字段做预分配；魔数/尾部校验齐全。
- **protobuf 解码**：`registry.decode`/`dynamic` 用 `ParseFromString` 并对异常返回 None，对 8MB 上限内畸形体安全、不越界不 OOM。
- **坏包防崩**：`session.feed`/`session._run`/`router.dispatch` 对畸形包、坏 handler 的 `except Exception`（`# noqa: BLE001`）大多是“一个坏请求不能崩服”的刻意防御，定位合理。
- **存档原子写**：tmp + `replace` 保证原子替换，不会写坏档。
- **路由注册**：cmd id 与 handler 注册一致；`challenge.stage_index`、未知 `challenge_id` 均有钳制。
- **编码/工具**：无 UTF-8 BOM 崩溃风险；无除零；`decode` 字节偏移与 `frame.py` 布局一致。
