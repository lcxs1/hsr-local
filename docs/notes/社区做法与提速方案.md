# 社区做法与提速方案（探索笔记）

> **状态**：探索期笔记（不是事实源，结论回填现行文档后才算数）　**适用版本**：4.6.54（build 16927089）/ 4.7.0（build 17108910）　**最后修订**：2026-11-11

本文回答一个问题：社区和其它参考工程到底怎么做的，我们能借什么、不能借什么、下一步怎么提速。
采集方式：本地七份工程只读检索；线上只做公开页面只读检索（本次按 AGENTS §6 的资料检索条目执行）。

---

## 0. 一句话结论

**社区没人去逆向客户端。** 他们的做法是三件事：把范围缩到“能进能打”、把数据换成按版本发布的数据包、
剩下靠人工试玩。挑战部分尤其明显——pearl-sr / dahlia-sr 的 README 都写着
“MoC/PF/AS simulator with **custom stage selection**”，也就是**绕开官方的轮换关卡组 UI**，
直接让玩家选关打。我们卡住的三件事（下半黑屏、缺「物竞天择」、PF/AS 锁定）正好落在他们绕开的那块区域。

## 3. 三条社区共识

### 3.1 数据 > 代码

DanhengServer 的挑战代码只有 1359 行，但整套玩法能跑，靠的是 `Resources/ExcelOutput` 里**每张表的全量数据**
（`ChallengeConfigExcel` / `ChallengeGroupExcel` / `ChallengeTargetExcel` … 共 21 个挑战相关类）。
它的 `PacketGetChallengeScRsp.cs` 只有 36 行：配置表全量发 `challenge_list`，有通关记录就用记录覆盖，
`challenge_group_list` **只放领过星数奖励的组**。

对照我们：`data/endgame.json` 是从 pearl 的残表导的（只带 `ChallengeMazeConfig` 等 3 张），
**没有 `ChallengeGroup` 表**，所以组、轮换、解锁全是推出来的。这不是编码水平问题，是数据缺口。

### 3.2 挑战按“能打”交付，不按“官方流程”交付

pearl-sr 和 dahlia-sr 都明确写“custom stage selection”。配套的证据是 pearl 的 `onStartChallenge`
直接从请求里的 `challenge_id` 建战斗，`GetChallenge` 里把 `star = 7`、`taken_reward = 42` 写死
（等于“全部已通关已领奖”），从不发 `ChallengeSettleNotify`（全工程零命中）。
它们要的是**战斗模拟器**，不是复刻官方的轮换大厅。

### 3.3 验证靠人，没有自动化回归

七个工程里没有一个做协议级回归：DanhengServer 的 CI 只 `dotnet publish`，LunarCore 只 build，
pearl/Himeko/dahlia 连 CI 都没有，echium 的 `smoke_test.py` / `lineup_test.py` 是一次性脚本。

**这条对我们反而是好消息**：`hsr/replay.py` + `tools/golden` 抓包基线，社区没有等价物。
我们真正缺的是“把挑战链也纳入回放”，而不是“找别人现成的测试”。

### 3.4 能搬的三条 / 不该搬的三条

| 能搬 | 怎么搬 |
|---|---|
| 配置表驱动 | 补 `ChallengeGroup` 等缺表，`_challenge_list` / `_group_list` 改成照表生成，`export_*.py` 缺表即失败 |
| 自定义选关 | 保留“任意关卡直接可打”的能力，作为官方轮换未通前的兜底入口 |
| 版本化数据 | 每个客户端版本一份 `data/vendor/<version>/`，锁 build 号，不混用 |

| 不该搬 | 为什么 |
|---|---|
| `star = 7` / `taken_reward = 42` 写死 | 星级/奖励对玩家可见。**我们现在也这么干**（`hsr/game/handlers/challenge.py` 的 `CHALLENGE_STAR` / `CHALLENGE_TAKEN_REWARD`），属于临时占位；通关历史落库后要换成真实值 |
| 从不发 `ChallengeSettleNotify` | 我们的口径是官方流程，跳过结算会重现“打完不结算/无限刷怪” |
| 整体按“战斗模拟器”交付 | pearl/dahlia 的定位是开发者沙盒；我们要的是能正常玩的服，模拟器只能当兜底入口 |

## 4. 对我们的五条判断

1. **范围定得比所有参考都高**：我们做的是官方大厅 + 关卡组卡片 + 两段式 + 退出回大厅，参考工程全部绕开。
   这解释了为什么“隔壁有实现”帮不上忙——实现的是另一个东西。
2. **验证能力其实领先**：193 单测 + 5 链回放 + 抓包基线；把挑战链补进回放就能领先更多。
3. **数据是最大短板**：缺 `ChallengeGroup` / 轮换时间表 / 通关历史；这三样正是 UI 卡片与解锁的输入。
4. **双版本并行是债务**：社区按版本分仓库（`dahlia-sr-0.14.1`、`pearl-sr` 各挂一个版本），
   我们一个仓库同时背 4.6.54 和 4.7.0，每次改动都要考虑两套。
5. **“下半黑屏”别指望抄**：没有任何参考工程实现过官方口径的下半流程。

## 5. 30 天三条主线

| 主线 | 做什么 | 估时 | 风险 | 依赖 |
|---|---|---|---|---|
| **A. 回放机器人** | 把挑战链写进 [hsr/replay.py](../../hsr/replay.py)：`GetChallenge → StartChallenge → SceneCastSkill ×N → PVEBattleResult → 两段式 → LeaveChallenge`；再用 `tools/golden` 的真实请求 body 回灌 | 1–2 天 | 低（纯本地，不碰客户端） | 无 |
| **B. 契约差集工具** | 对每条下发消息列出“留默认值的字段”，与 DanhengServer 3.7 同名 `Packet*.cs` 的构造做集合差，人工判定必需性；结果进 `check.ps1` | 1 天 | 低 | 无 |
| **C. 数据管线** | `resource_convert.py`：ExcelOutput → JSON；补 `ChallengeGroup` / 轮换表；`export_endgame.py` 加“缺表即失败”的覆盖断言 | 1–2 天 | 中（依赖数据来源授权） | AGENTS §6 客户端配置表 |
| **D. 口径决策** | 拍板“模拟器口径（选关，先能打）”还是“官方口径（大厅+轮换）”；两者并存时怎么标注 | 半天讨论 | 低 | 人决策 |

建议顺序：**A → D → B → C**。A 不依赖任何人，做完立刻把真机往返砍一半；D 决定后面要不要继续追官方口径；
B 是长期防坑；C 的数据来源按 AGENTS §6 已预授权，可直接跑（落盘记 SHA256 并校验 build）。
